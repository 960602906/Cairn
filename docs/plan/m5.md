## 1. 目标

**完成标准**（架构 §26）：可以分发给他人安装。

具体来说：

1. 在干净的 Windows 11 当前受支持版本（至少 24H2，正式支持基线）与 Windows 10 22H2（best-effort，微软已结束支持）、普通用户账户（非管理员）上，可以用 NSIS 安装包完成安装、启动、创建项目、运行任务、卸载；安装和运行都不要求管理员权限。
2. 安装包是 `0.1.0` 公开 beta，Windows x64、按用户安装；同一台机器只允许一个应用实例写数据；任务栏、通知与快捷方式使用固定的应用身份。
3. 命令默认在 Windows 受限工作区沙箱中运行：工作区可写，工作区外不可写，默认没有管理员权限；受限令牌回退时网络无法隔离，必须明确标注并按审批执行；AppContainer 仅保留实验/诊断能力，不作为默认档位。需要脱离沙箱时显式升级并留痕。沙箱不是虚拟机级安全边界，失败时默认关闭；具体配置档、网络语义与回退见 ADR-0034。
4. 没有安装 Git 的机器也能使用检查点：优先使用本机 Git（≥ 2.32），否则使用随安装包分发的裁剪版 MinGit；两者都不可用时检查点降级，但写文件类改动仍可撤销。
5. 自动更新可用：能从 `0.1.0` 检查、下载、校验并安装 `0.1.1`；更新源是公开只读的 HTTPS 静态源，客户端不携带仓库令牌；更新不会在任务运行中静默重启；断网、代理、损坏包、签名不符、磁盘不足都有明确状态。
6. 取得代码签名证书时，安装包、主程序与卸载程序都带时间戳签名，CI 校验签名后才发布；未取得证书时只能发布明确标注的 unsigned beta，且不得宣称已具备发布者校验。
7. 用户可以找到版本、构建信息、更新状态、第三方许可、GPL 源码获取方式、隐私说明与诊断包入口；界面文案中英齐全，不显示金额。
8. 质量门槛：四项覆盖率不低于 95%；`pnpm format:check`、`pnpm typecheck`、`pnpm lint`、`pnpm check:i18n`、`pnpm check:licenses`、`pnpm test:coverage`、`pnpm build`、`pnpm e2e`、`pnpm smoke`、`$env:CAIRN_PERF='1'; pnpm test:perf` 全部通过；新增打包、已安装应用与更新链路测试通过；Windows 与 Ubuntu CI 同时通过。

### 1.1 不在本轮范围内

- **跨会话长期记忆**（ADR-0019）：M5 不实现存储、提取、注入或管理界面；M6 之后单独立项，避免再次挤压发布。
- **macOS、Linux 正式适配与打包**：M6；M5 只保证沙箱与打包实现不把 Windows 假设写进跨平台接口。
- **ARM64、32 位、Microsoft Store / MSIX、便携版、per-machine 安装**：M5 只做 Windows x64 按用户 NSIS；其余在真实需求出现后评估。
- **遥测、崩溃上报、账号与云端同步**：M5 不做；诊断包仍是本地导出。更新检查只访问更新源，不发送项目内容或凭据。
- **MCP 服务进程与 Agent 宿主不在命令沙箱内**：沙箱只覆盖 `run_command` 与 `start_command` 启动的进程树；MCP 子进程仍以应用用户权限运行，Agent 宿主自身的文件访问继续依赖路径校验与权限引擎。界面与文档不得把“命令沙箱”表述为覆盖全部进程。
- **自动回滚到旧版本**：`electron-updater` 不提供降级；M5 提供“保留上一版安装包 + 数据备份 + 明确阻断降级”的恢复路径，不做二进制自动回滚。
- **企业分发、GPO、离线批量部署、代理配置界面**：M5 只验证系统代理与直连；不做企业安装器。
- **插件市场、工作流 DAG、审查循环、团队模板**：继续留给后续里程碑。
- **新模型提供方**：现有 OpenAI / Anthropic / Gemini 三种线路格式已覆盖接入需求，M5 不单列厂商。
- **网站、文档站与账号体系**：M5 只交付安装包、应用内说明与仓库内发布文档。

### 1.2 任务约定

沿用 M3、M4 的约定：

- 一个子任务一个 PR，标题形如 `feat(release): Windows 安装包 [M5-02]`；合并后再开始下一个。跨任务的共享接线在 §6 单独列出。
- 每个 PR 同时更新本文：§4 的“状态”一行，以及对应任务下的“实施记录”（做了什么、与计划的差异及原因）。
- 提交前在仓库根目录运行：`pnpm format:check`、`pnpm typecheck`、`pnpm lint`、`pnpm check:i18n`、`pnpm check:licenses`、`pnpm test:coverage`（四项覆盖率不低于 95%）。改到桌面端时再运行 `apps/desktop` 下的 `pnpm build`、`pnpm e2e`；涉及打包时运行 `pnpm package:dir` 与已安装应用冒烟；最终收尾再运行 `pnpm smoke`、`$env:CAIRN_PERF='1'; pnpm test:perf`。
- 界面文案全部走 i18n（ADR-0013），`packages/i18n/locales/zh-CN` 与 `en-US` 同时补齐；lint 规则 `cairn/no-literal-ui-text` 不允许在组件里写死文字。
- 组件只用设计令牌（`styles/tokens.css`）的颜色；界面 PR 附浅色、深色截图。
- 新依赖取最新稳定版，通过许可证检查（ADR-0014，`scripts/license-exceptions.json`）；随应用分发的外部二进制必须登记到 `scripts/bundled-binaries.json`，并提供许可证全文与源码获取方式。
- 新协议类型、事件、RPC 写在 `packages/protocol`（zod）；主进程实现在 `apps/desktop/src/main/services/`，经 `renderer-gateway.ts` 暴露给渲染进程；`packages/core` 不引用 DOM、Node、Electron 类型。
- API Key、MCP 令牌等凭据只经过凭据服务（ADR-0010，`safeStorage`），不写进安装包配置、日志、更新元数据、诊断包、PR 描述。
- 涉及新的架构决定时补 ADR（编号从 0034 起，见 §2.4），在任务的“实施记录”里引用。
- 发布相关密钥（签名证书、更新源凭据、GitHub 令牌）只放在 CI secrets；本地构建默认不签名、不发布、不写更新源。
- 新增事件与可选字段保持向后兼容；如果改变已有字段的含义或必填性，提升 `EVENT_SCHEMA_VERSION` 并补迁移/恢复测试。

## 2. 范围裁决与前置结论

### 2.1 架构合同拆解

架构 §26 把 M5 定义为“命令沙箱、自动更新、签名与 Windows 安装包（附带精简版 MinGit）”。逐项落到任务：

| 架构要求 | 计划任务 | 权威证据 |
|---|---|---|
| Windows 安装包 | M5-02 | 干净 Windows 10/11 上 NSIS 安装、启动、卸载；已安装应用冒烟 |
| 按用户安装、无需管理员 | M5-02 | 普通用户账户安装与运行；安装日志与权限断言 |
| 命令沙箱 | M5-00、M5-04、M5-05 | 沙箱 API 预研；真实命令兼容性矩阵；越界写/网络/管理员权限测试；界面与事件留痕 |
| 自动更新 | M5-06、M5-07、M5-08 | 本地静态更新源端到端测试；损坏包/签名不符/断网/代理测试；发布流水线 |
| 代码签名 | M5-08 | `signtool verify` 或云签名验证；安装包、主程序、卸载程序签名；CI 门禁 |
| 精简版 MinGit | M5-03 | 移除 PATH 中的 Git 后检查点仍可用；体积、许可证、源码获取方式 |
| 可以分发给他人安装 | M5-09、M5-10 | 首次运行材料、许可与隐私、诊断、发布验收清单 |

### 2.2 现有基础与缺口

| 能力 | 现状 | M5 动作 |

| 构建 | `electron-vite` 产出 `out/main`、`out/preload`、`out/renderer`、`out/bin`、`out/THIRD_PARTY_NOTICES.txt` | 增加 `electron-builder` 打包与安装包，验证 asar 与 unpack |

| 许可与材料 | 仓库没有 `LICENSE`；有第三方声明生成器 | EULA/隐私说明、第三方声明、GPL 源码获取方式、安装说明 |

### 2.3 已落定的范围决策

| 决策 | 结论 | 影响 |
|---|---|---|
| M5 是否包含长期记忆 | 不包含；只做发布硬化 | 记忆在 M6 之后单独立项 |

## 3. 技术选型

| 用途 | 选择 | 说明 |
|---|---|---|
| 打包 | `electron-builder` 26.18.0（NSIS） | 与 M0 SQLite spike 已验证版本一致；只做 Windows x64 |
| 安装器 | NSIS，按用户、可选安装目录、保留用户数据 | 不要求管理员；卸载不删除 `%APPDATA%\Cairn` |
| 更新 | `electron-updater` 6.8.11 + generic provider | 公开只读 HTTPS；支持 blockmap 差量和 staged rollout |
| 签名 | `signtool` / 云签名服务（OV/EV） | 证书与密码只进 CI secrets；时间戳必须配置 |
| 沙箱 | 现有 `koffi` 调 Windows API | 不新增原生依赖；AppContainer 与受限令牌各做预研 |
| MinGit | 官方 MinGit 2.56.0.4 64 位，固定 SHA256 | 构建时下载、裁剪、校验；不提交二进制到仓库 |
| 版本 | 根 `package.json` 为唯一版本源 | 构建前校验桌面包版本一致；`app.getVersion()` 读取打包版本 |
| 发布 | GitHub Actions `windows-latest` + 静态源上传 | 产物校验、签名、校验和、发布说明；构建来源证明视仓库套餐支持情况生成 |
| 测试 | Vitest + Playwright + 本地静态更新源 + 干净 Windows VM | 单元/集成/组件/端到端/安装级证据分层 |

## 5. 任务详情

### M5-00 预研与文档基线

- **目的**：在写实现前确认 Windows 沙箱、打包、更新与 MinGit 的 go/no-go，避免把不可行的方案写进任务。
- **交付物**
  - `docs/plan/m5-spikes.md`：每个 spike 的假设、步骤、环境、原始结果、结论与回退。
  - ADR-0034、ADR-0035、ADR-0036 草稿；ADR-0008、ADR-0012、ADR-0014 的 M5 变更草稿。
  - 可复现脚本：沙箱兼容性矩阵、MinGit 裁剪与校验、本地静态更新源、打包产物检查。
  - 发布前置条件清单：证书、更新源、代码签名账户、测试机。
- **预研项**
  - **S1 沙箱兼容性**：用 `koffi` 调 Windows API，比较三种配置：
    1. `restricted-workspace`：受限令牌（禁用最大权限、LUA）+ 低完整性 + Job Object + 工作区 ACL；网络可用。
    2. `appcontainer-workspace`：AppContainer + 工作区 ACL；默认不授予网络能力，审批后以带 `internetClient` / `privateNetworkClientServer` 的配置重启命令。
    3. `none`：当前行为。

    在 Windows 11 当前受支持版本（至少 24H2）与 Windows 10 22H2 上用真实命令测：`node --version`、`pnpm --version`、`pnpm install`、`git status`、`python -c`、`dotnet --info`、`npm test`、`tsc`、`eslint`、`vitest`、`rg`、`git commit`、`npm run dev`（长进程）。记录：stdout/stderr/退出码、中文输出、子进程是否继承沙箱、能否写工作区/临时目录/用户目录/系统目录、能否读包管理器缓存、能否联网、是否需要管理员、启动开销。

    **go/no-go 门槛**：`node`、`pnpm`、`git`、`python`、`dotnet`、`tsc`、`vitest`、`rg` 必须全部可运行；`pnpm install` 在授予网络能力后必须成功；工作区外写入、系统目录写入与管理员操作必须被拒绝；子进程必须继承沙箱；失败命令不得留下进程树。AppContainer 达到以上门槛才作为默认档；只允许非关键命令（如个别全局缓存路径）失败，且必须有明确 workaround；否则回退受限令牌，并在 ADR 中记录“网络未隔离”的后果。

    **普通用户前提**：必须验证 `CreateAppContainerProfile`、`SetTokenInformation`（完整性级别）、`CreateProcessAsUser` / `CreateProcessWithTokenW`、工作区 ACL 授予在标准用户（非管理员、无 UAC 提权）下可用。任一步骤要求管理员权限时，该方案不能作为默认安装形态；如果 AppContainer 与受限令牌都不可行，M5 必须重新裁决沙箱目标，不能把“需要一次性提权”包装成“按用户安装”。
  - **S2 打包**：`electron-builder --dir` 与 NSIS 各跑一次；检查 `app.asar`、`app.asar.unpacked`、`out/bin/rg.exe`、`koffi`、`better-sqlite3`、`resources/skills`、`THIRD_PARTY_NOTICES.txt`、`agent-host.js`、preload `.cjs`；在干净用户账户安装并启动。
  - **S3 更新**：本地 HTTPS 静态源 + `latest.yml` + blockmap；从 `0.1.0` 更新到 `0.1.1`；测断网、404、损坏包、错误 SHA512、签名不符、代理、磁盘不足、下载中断。
  - **S4 MinGit**：官方 MinGit 2.56.0.4 64 位 zip 的 SHA256、解压体积、裁剪名单、`git init/add/commit/diff/checkout/rev-parse/cat-file` 可用性、许可证与源码获取方式。

  - 设置/诊断显示当前 Git 来源（本机/随包/不可用）与版本。

### M5-04 命令沙箱核心

- **目的**：把命令执行从“审批 + 路径校验 + Job Object”提升为 OS 级隔离，并明确它不是虚拟机级安全边界。
- **交付物**
  - `packages/shell` 增加沙箱类型与 Windows 实现：受限令牌、低完整性、AppContainer、工作区 ACL、网络能力、进程树。
  - `apps/desktop/src/main/services/sandbox-service.ts`：解析策略、创建/复用 AppContainer 配置、清理、能力探测、诊断。
  - 协议：`host.init` 增加 `sandbox` 策略；`run_command` / `start_command` 传递策略；`command.started` 与 `tool.started` 增加可选 `sandbox` 字段（向后兼容）。
  - 设置：默认沙箱档位（只允许 `workspace-write` / `read-only`）、网络策略、沙箱不可用时的行为；权限引擎增加“脱离沙箱”审批。`danger-full-access` 不作为可持久化的默认值。
- **实施要点**
  - 默认 `workspace-write`：工作区与专用临时目录可写；系统目录、程序目录、其他用户目录只读或不可读；包管理器缓存与工具链配置按白名单授权；默认无网络。
  - 读取白名单只包含运行开发命令必需的目录与文件，例如 `%USERPROFILE%\.gitconfig`、`%APPDATA%\npm`、`%LOCALAPPDATA%\pnpm`、`%USERPROFILE%\.nuget`、`%USERPROFILE%\.dotnet`、语言 SDK 目录；`.ssh`、`.aws`、`.config/gcloud`、浏览器配置、凭据存储与项目外私钥必须显式拒绝。项目内 `.npmrc` 可读，用户级 `.npmrc` 默认不读；需要时走脱离沙箱审批。
  - `read-only`：工作区只读，临时目录可写；适合只读子 Agent 与计划模式。
  - `danger-full-access`：当前行为；必须逐次或按会话审批，不能通过“始终允许”静默持久化。
  - AppContainer 优先；如果 S1 证明兼容性不可接受，回退到受限令牌，并在设置与文档中标注“网络未隔离”。
  - 沙箱创建失败不得静默降级：默认失败关闭；用户显式选择“本次不使用沙箱”后才执行，并写入事件。
  - 沙箱只覆盖命令进程树；MCP 服务、Agent 宿主与主进程不在沙箱内。界面与诊断必须能区分“命令沙箱”和“整个应用隔离”，避免错误安全预期。
  - 网络能力分为“公网”和“本地/私网”：开发服务器、localhost 回调等使用 `privateNetworkClientServer`；普通外网使用 `internetClient`；默认都不授予。
  - 命令结束、取消或应用退出时清理专用临时目录；AppContainer 配置按安装 ID 复用，卸载后的残留由安装器或设置中的清理入口处理。
  - 保持现有编码、退出码、超时、进程树结束与环境清洗语义；沙箱只改变隔离边界，不改变命令协议。
  - 不把项目路径、用户名或凭据写入沙箱配置名；AppContainer 名称使用安装 ID 与用户 SID 的稳定哈希。
  - 沙箱档位与权限预设正交：权限预设决定“是否询问”，沙箱档位决定“OS 隔离到什么程度”；计划模式与只读 Agent 强制 `read-only` 沙箱，不能靠用户预设放宽。
- **验收**：表驱动测试覆盖工作区写、工作区外写、系统目录写、管理员操作、网络拒绝/允许、子进程继承、取消与超时；真实命令兼容性矩阵达到 M5-00 设定的门槛；沙箱不可用时失败关闭；事件中能看到实际沙箱档位。
- **依赖**：M5-00、M5-01。
- **风险**：沙箱会破坏部分开发命令；这是产品取舍，不是实现缺陷。必须用真实命令矩阵与显式升级路径管理，而不是悄悄放宽。

**实施记录（2026-11-10）**

- 协议：新增 `packages/protocol/src/sandbox.ts`（档位、网络、策略、执行描述、能力、不可用行为与默认值）。`Settings` / `SettingsPatch` 增加 `sandboxProfile`、`sandboxNetwork`、`sandboxUnavailable`；`danger-full-access` 不在可保存类型中，读取已有文件时也会被丢弃。`host.init.sandbox`、`host.command.start.sandbox`、`command.started` / `tool.started` 的 `sandbox` 全部为可选字段，旧客户端与旧事件不受影响。
- `@cairn/shell`：新增 `sandbox/`，包含 MSVCRT 命令行引用与 UTF-16 环境块、System32 `icacls` 执行器、完整性标签、AppContainer 配置/ACL/网络能力、Job Object、能力探测、koffi 绑定与 `createSandboxRunner`。输出写入专用临时文件并用 `StringDecoder` 跨块解码；超时、取消与命令结束都结束整个 Job。任何准备步骤失败都抛 `SandboxError`，没有静默回退路径。
- 只读档位：`workspace-write` 把工作区设为低完整性（`(OI)(CI)L`），`read-only` 设为中完整性（`(OI)(CI)M`），低完整性进程无法写入；没有删除或重写工作区 ACL。专用临时目录始终为低完整性。
- 网络：受限令牌不能隔离网络，`networkIsolated` 如实为 false；只有实验性 AppContainer 才按 `none` / `internet` / `private` 授予网络能力 SID。
- 主进程：`sandbox-service.ts` 解析设置、启动时探测一次能力（探测异常缓存为 `sandbox.probe_failed` 并上报，不会反复重试）、按安装标识的 SHA-256 生成 AppContainer 名称、提供宿主初始化、后台命令执行器、诊断与清理。`command-service` 与 `host-supervisor` 把策略与执行器接入 `command.started` 与 `host.init`；没有执行器时事件仍写 `mechanism: none` 与 `sandbox.unavailable` 原因，避免界面误以为沙箱生效。
- 宿主：`builtin-tools` 按能力创建并复用沙箱执行器，把策略与执行描述传给 `run_command` / `start_command`；只读 Agent 在根运行与委派子运行都被强制为 `read-only`，不能靠父运行的写入档位或权限预设放宽。计划模式已经由 `planModeGuard` 拒绝全部执行/写入类工具，因此不需要为单轮切换可变沙箱策略。
- 权限：新增 `sandboxGuard`，只作用于 `run_command` / `start_command`。`danger-full-access` 每次审批且不可被“始终允许”覆盖；沙箱不可用时默认拒绝（`deny`），设置为 `ask` 时每次审批后以应用用户权限执行；平台不支持时不拦截，保持 M6 之前的现有语义。
- 测试：新增协议、命令行、完整性、ACL、Job、能力探测、执行器（超时/取消/输出分片/AppContainer）、koffi 绑定（假 koffi 校验参数与缓冲区布局）、沙箱服务、权限守卫、设置、命令服务、宿主、内置工具与工具的用例。本机手工验证真实命令矩阵：工作区内写入成功、工作区外写入被拒、`read-only` 档位写入被拒、中文输出正常、500 ms 超时清理父子进程、取消生效、`net session` 被拒。
- 未验证/留给后续：干净 VM、标准用户账户、Windows 10、中文用户名与长路径属于 M5-10；真实网络隔离仍未实现（受限令牌档位明确标注“网络未隔离”）；设置页、审批卡片、终端标记与诊断包字段在 M5-05 接入。
- 与计划的差异：默认机制确定为受限令牌（M5-00 已判定 AppContainer 工具链不可用）；只读档位采用完整性标签而不是 ACL 删除；计划模式用现有守卫拒绝执行，而不是在单轮切换可变沙箱策略；`danger-full-access` 的审批实现为不可覆盖，强于“逐次或按会话审批”的最低要求。

### M5-05 沙箱交互、设置与可观测性

- **目的**：让用户知道命令在什么隔离级别运行、为什么被拒绝、如何安全升级。
- **交付物**
  - 终端/工具卡片的沙箱标记（如“沙箱：工作区可写 / 无网络”）；运行检查器与命令历史显示实际档位。
  - 审批卡片展示沙箱档位、网络策略、被拒绝的路径/操作与升级选项；升级审批文案明确“将在沙箱外运行”。
  - 设置页：默认沙箱档位、网络策略、沙箱不可用时行为、诊断入口；不提供“永久关闭沙箱”的一键开关。
  - 错误码与 i18n：沙箱不可用、路径被拒绝、网络被拒绝、AppContainer 创建失败、命令需要升级。
  - 诊断包增加沙箱能力探测结果（不包含项目内容与凭据）。
- **验收**：组件测试覆盖标记、审批、错误与设置；e2e 在沙箱开启时完成一次工作区写入与一次被拒绝的工作区外写入；浅色/深色截图；中英文案齐全。
- **依赖**：M5-02、M5-04。
- **风险**：错误提示如果只说“失败”，用户会反复重试；必须给出具体原因与下一步。

**实施记录（2026-11-10）**

- 协议：新增 `SandboxStatus` 与 `sandbox.status`；审批请求增加可选 `sandbox` / `overridable`；工具视图、宿主审批与诊断摘要增加沙箱字段。`danger-full-access` 仍不能保存为默认值。
- 渲染进程：新增 `SandboxBadge` 与共用文案 `sandbox-labels`，终端卡片、工具时间线与审批卡片显示实际档位、机制与网络状态；未沙箱化时用错误色并写明原因。审批不可覆盖（`overridable: false`）时不显示“始终允许”，数字键 2 不再生效。
- 设置页：命令沙箱分组提供默认档位、网络策略、不可用行为与能力状态（实际机制、回退说明、四项探测、网络状态、失败提示）。受限令牌下明确显示“网络未隔离”；没有“永久关闭沙箱”的一键开关。

- 错误与 i18n：新增 `sandbox.appcontainer_failed`；中英文补齐沙箱档位、网络、机制、原因、警告、审批理由与设置文案。

### M5-06 自动更新服务

- **目的**：让已安装的 beta 用户能安全地收到新版本，同时不打断正在运行的任务。
- **交付物**
  - `apps/desktop/src/main/services/update-service.ts`：检查、下载、校验、安装、取消、状态推送；使用 `electron-updater` generic provider。
  - 协议：`update.status`、`update.check`、`update.download`、`update.install`、`update.cancel`；状态变化推送渲染进程。
  - 设置：自动检查开关、通道（stable/beta）、上次检查时间、跳过版本；默认自动检查、手动安装。
  - 构建注入：`CAIRN_UPDATE_URL`、通道与 `publisherName`；开发模式与 `CAIRN_UPDATE_DISABLE=1` 时禁用。
  - 更新前备份：数据库、`settings.json`、凭据文件元数据（不复制明文密钥）；保留最近两份；记录备份路径到日志与诊断包。
- **实施要点**
  - 启动后延迟检查（如 30 秒），之后每 6 小时一次；手动检查立即执行；失败只记录状态，不弹错误风暴。
  - `autoDownload = false`、`autoInstallOnAppQuit = false`；下载完成由用户确认重启，或在无运行任务时退出安装。
  - 有运行中会话、待审批或检查点恢复时，禁止静默重启；提示“任务结束后更新”或让用户显式取消任务。
  - 校验 SHA512、文件大小与 Authenticode（配置了 `publisherName` 时）；校验失败删除临时包并报告。
  - 禁止降级：`allowDowngrade = false`；数据库 `SchemaTooNew` 作为第二道防线。
  - 更新源只允许 HTTPS；不允许把 GitHub 令牌、签名密码或私有源凭据打进客户端。
  - 支持 blockmap 差量下载；下载中断可重试；磁盘空间不足提前提示。
  - 支持 `stagingPercentage` 的读取与测试（M5 只使用 0 或 100），保留后续灰度能力；下载失败、取消或校验失败后清理临时包与半成品。
- **验收**：本地静态源端到端测试 `0.1.0 → 0.1.1`；断网、404、损坏包、错误哈希、签名不符、磁盘不足、代理、运行中更新全部有确定状态；更新后数据库与设置可恢复；不允许降级。
- **依赖**：M5-02。签名字段在 M5-08 接入；更新器自身的测试不依赖证书，未签名包按 unsigned beta 路径验证。
- **风险**：更新服务最容易在“用户正在跑任务”时造成数据损失；必须把运行中保护做成硬约束，而不是界面提示。

- **目的**：让更新可见、可控、可恢复。
- **交付物**

  - 启动后的可用更新提示（非模态），运行中任务的延迟更新提示；下载完成后的重启确认。
  - 关于页显示版本、构建信息、通道、更新源与第三方许可入口。
  - i18n 与浅色/深色截图。
- **验收**：组件测试覆盖所有状态；e2e 用本地静态源完成检查 → 下载 → 重启提示；运行中会话时重启被阻止；错误状态可重试；中英文案齐全。
- **依赖**：M5-06。
- **风险**：更新提示不能变成模态打断；默认非模态，只有重启确认是模态。

### M5-08 代码签名与发布流水线

- **目的**：把“本地能构建”变成“可验证、可重复、可追溯的发布”。
- **交付物**
  - `.github/workflows/release.yml`：标签 `v*` 触发；Windows runner 构建、测试、打包、签名、校验、生成校验和与更新元数据、上传静态源、创建发布说明。
  - 签名脚本：支持 PFX + 密码或云签名；时间戳；`signtool verify /pa /all`；安装包、主程序、卸载程序全部验证。
  - 发布产物：NSIS 安装包、blockmap、`latest.yml`（stable）或 `beta.yml`（beta）、`SHA256SUMS`、`THIRD_PARTY_NOTICES.txt`、依赖清单、发布说明；仓库套餐支持时附构建来源证明（artifact attestation），否则记录 commit SHA、构建日志与产物哈希。
  - 发布门禁：签名失败、校验失败、测试失败、许可证失败、i18n 失败、产物缺失任一出现都不得发布。
  - 发布文档：`docs/dev/release.md`，包含证书轮换、更新源配置、回滚与紧急撤包步骤。
- **实施要点**
  - 证书与更新源凭据只从 CI secrets 读取；日志不得输出密码、PFX 内容或完整令牌。
  - `publisherName` 必须与证书主题一致；否则 `electron-updater` 会拒绝更新。
  - 未取得证书时：发布流程标记 `unsigned beta`，跳过发布者校验，发布说明与安装界面明确 SmartScreen 风险；不得把 unsigned 包放进 stable 通道。
  - 上传采用最小权限令牌；发布后从公开 URL 重新下载并校验 SHA256，确认静态源可匿名访问。
  - 发布说明来自 `CHANGELOG.md`，不手工复制；版本标签与 `package.json` 一致。
  - 保留上一版安装包与 blockmap，支持紧急撤包与手动回退。
- **验收**：在测试标签上完整跑通一次 dry-run；签名验证通过；公开 URL 可下载；`latest.yml` 指向正确版本与哈希；错误签名/缺失产物会让流水线失败；生成构建来源证明时其可验证，否则 commit SHA、构建日志与产物哈希齐全；发布文档可被第二个人按步骤执行。
- **依赖**：M5-02、M5-06。
- **风险**：证书申请周期是外部阻塞；必须在 M5-00 启动，不能等到 M5-08。

### M5-09 首次运行、许可与分发材料

- **目的**：让第一次安装的用户知道这是什么、数据在哪里、密钥如何保存、更新会访问哪里。
- **交付物**
  - `LICENSE`/EULA（M5 beta 使用专有许可，M6 开源前替换）、`PRIVACY.md`、`docs/dev/install.md`、`docs/dev/troubleshooting.md`。
  - 首次运行欢迎页/提示：产品用途、数据目录、API Key 保存在本机、更新检查会访问更新源、诊断包可能包含日志但会脱敏；不强制登录。
  - 没有配置模型提供方时，引导到设置页；不阻塞用户浏览已有数据。
  - 关于页/设置页可打开第三方许可、GPL 源码获取方式、隐私说明与诊断包。
  - 安装包内附带 `THIRD_PARTY_NOTICES.txt`；卸载说明明确保留用户数据与手动清理方式。
- **实施要点**
  - 不在首次运行收集遥测；不要求账号；不默认上传诊断包。
  - 明确说明：模型请求会把所选上下文发送给用户配置的模型提供方；API Key 由系统凭据加密保存在本机；更新检查会访问更新源；诊断包可能包含脱敏后的日志。
  - 许可与隐私文案中英双语；中文为默认语言时也提供英文版本。
  - 首次运行提示只出现一次，可在设置中重新查看；不阻断已有用户升级。
  - 说明“沙箱不是虚拟机”“未签名 beta 可能触发 SmartScreen”等限制。
- **验收**：干净安装首次启动看到提示；没有提供方时能进入设置；关于页能打开全部材料；卸载说明与数据保留行为一致；i18n 检查通过。
- **依赖**：M5-02、M5-07。
- **风险**：法律文本需要项目所有者确认；计划默认专有 beta 许可，M6 开源前必须替换。

### M5-10 安装、升级、卸载验收与发布收尾

- **目的**：在真实 Windows 环境证明“可以分发给他人安装”，并补齐文档与发布记录。
- **交付物**
  - 干净 VM 验收矩阵：Windows 11 当前受支持版本（至少 24H2，正式支持）、Windows 10 22H2（best-effort）；普通用户；中文系统区域设置；中文安装路径与用户名；无 Git；有旧版 Git；有代理；断网；低磁盘；高 DPI/多显示器；Windows Defender 开启。
  - 安装 → 首次运行 → 配置模型 → 创建项目 → 沙箱内运行命令 → 创建/恢复检查点（无 Git 环境）→ 更新到下一版 → 卸载 → 重装恢复数据。
  - 全流程 e2e：打包应用启动、沙箱命令、更新检查、关于页/许可、诊断包；组合 spec 只验证接线。
  - 发布记录：`docs/plan/m5-report.md` 或本文实施记录，包含构建号、签名指纹、产物哈希、测试结果、已知问题。
  - 架构与 ADR 更新：§24 构建发布、§17 安全、§26 里程碑、ADR-0034～0036 定稿；README 当前计划更新到 M5。
- **验收**：§10 完成检查清单逐项勾选；所有质量门槛通过；干净 VM 矩阵无阻塞问题；发布包可匿名下载并通过哈希/签名验证；文档与实现一致。
- **依赖**：M5-03～M5-09。
- **风险**：干净 VM 验收容易被“开发机已装依赖”掩盖；必须使用没有 Node、没有 Git、没有构建工具的账户/机器。

## 6. 共享接线与迁移顺序

### 6.1 数据库迁移

M5 预计不新增数据库迁移：更新偏好与通道写入 `settings.json`，沙箱策略来自设置与 Agent/会话配置，构建信息来自构建产物。

如果实现中发现必须落库，按既有规则新增 `0016-*`，同时补内存实现、SQLite 实现与 `store-contract` 契约测试；不得跳过迁移编号，不得让旧版本打开新数据库。

升级前备份复用 `migrateDatabase` 的 `VACUUM INTO` 备份；`SchemaTooNew` 继续作为降级阻断。更新服务的额外备份只覆盖数据库、设置与凭据元数据，不复制明文密钥。

### 6.2 共享接线

以下文件会被多个任务同时改动，按“先协议、后实现、最后界面”的顺序合并：

- `packages/protocol/src/contracts/renderer-main.ts`：`app.info`、`update.*`、沙箱设置。
- `packages/protocol/src/contracts/host-main.ts`：`host.init.sandbox`、`host.init.gitBinary`。
- `packages/protocol/src/events.ts`：`command.started` 与 `tool.started` 的可选 `sandbox` 字段。
- `apps/desktop/src/main/services/renderer-gateway.ts`：新 RPC 的处理器与推送。
- `apps/desktop/src/main/index.ts`：单实例、AppUserModelID、Git 定位、沙箱服务、更新服务。
- `apps/desktop/src/agent-host/host.ts`：沙箱策略传递、Git 二进制使用。
- `packages/i18n/src/resources.ts`：新命名空间（`update.json`、`sandbox.json`、`about.json`、`onboarding.json`）。
- `apps/desktop/electron.vite.config.ts`：如果新增工作区包或构建注入，加入 `workspacePackages` 或 `define`。
- `apps/desktop/electron-builder.yml`、`scripts/`、`.github/workflows/release.yml`：发布链路。

### 6.3 事件与顺序

- 沙箱档位不新增会话级事件；`command.started` 与 `tool.started` 的可选 `sandbox` 字段记录实际执行档位，旧事件缺少该字段时按“未知/未启用”展示。
- 更新状态是应用级状态，不写入会话事件流；通过 `update.status` 推送，避免污染会话历史与活动中心。
- 更新安装前必须先结束或暂停所有宿主写入；安装重启后仍按既有事件恢复流程回放。
- 沙箱升级审批与现有审批共用 `approval.*` 事件，但必须带 `sandbox` 原因，且不得生成跨会话的永久放行规则。

## 9. 计划自审

本计划按“架构合同 → 现有代码 → 发布失败模式 → 任务依赖 → 验收证据 → 范围一致性”的顺序做了多轮自审。

### 9.1 第一遍：架构合同逐项

架构 §26 的五个交付项（沙箱、自动更新、签名、Windows 安装包、MinGit）都能在任务表中找到唯一归属；没有把“发布”拆成只有打包而没有更新/签名，也没有把 MinGit 当成打包的附属细节。发现并修正：

- 初稿只写“自动更新”，没有写更新源必须匿名可读。仓库私有，若把 GitHub 令牌打进客户端会形成严重凭据泄露；已改为 generic 公开只读静态源，并把“发布后公网重新下载校验”列为验收。
- 初稿把签名当成打包步骤。实际上证书申请是外部阻塞，且 `publisherName` 决定更新器是否校验发布者；已把证书启动提前到 M5-00，并区分 signed stable 与 unsigned beta。
- 初稿没有把“无 Git 机器”作为独立验收环境。MinGit 的意义正是在没有 Git 的机器上可用；已要求干净 VM 的 PATH 中完全没有 Git。

### 9.2 第二遍：现有代码现状

对照当前代码后补充了初稿遗漏的发布前置条件：

- 当前没有 `electron-builder.yml`、没有 `electron-updater`，版本仍是 `0.0.0`；M5-01、M5-02、M5-06 不能假设已有基础设施。
- 当前没有 `app.requestSingleInstanceLock()` 与 `app.setAppUserModelId()`；两个实例会同时打开数据库，通知也没有稳定身份。已加入 M5-01，并明确单实例锁必须在数据库打开之前。
- 检查点只通过 PATH 找 `git`，`host.init` 没有 Git 二进制字段；M5-03 必须同时改主进程、宿主与改动集服务，不能只把 MinGit 放进安装目录。
- `better-sqlite3`、`koffi`、`@vscode/ripgrep` 与 `out/bin` 的打包路径各有特殊处理；已把 asarUnpack 与已安装应用冒烟列为 M5-02 的核心证据。
- 仓库没有 `LICENSE`；分发前必须补 EULA/隐私说明。已加入 M5-09，并标注 M6 开源前替换。
- 初稿没有区分“命令沙箱”和“整个应用隔离”；MCP 服务进程与 Agent 宿主仍以应用用户权限运行。已把这一边界写入非目标、M5-04 与文档要求，避免把命令沙箱宣传成全局安全边界。

### 9.3 第三遍：发布失败模式

按“用户拿到安装包之后会发生什么”检查，补充了：

- 断网、代理、404、损坏包、哈希错误、签名错误、磁盘不足、下载中断。
- 更新时正在运行任务、存在待审批、检查点正在恢复。
- 数据库版本比应用新、升级后迁移失败、设置文件损坏。
- 安装到非默认目录、中文用户名、长路径、无管理员权限、SmartScreen。
- 没有 Git、Git 版本过低、MinGit 被裁剪坏、随包 Git 无法启动。
- 沙箱创建失败、命令需要网络、命令需要写工作区外、命令需要管理员。

对应任务都增加了明确的失败状态与验收，不再只写“成功路径”。

### 9.4 第四遍：依赖与顺序

- 沙箱与打包是两条独立主线；M5-02 不必等 M5-04，避免最长任务阻塞安装包。
- M5-05 依赖 M5-02 与 M5-04：没有安装包无法验证真实安装形态，没有沙箱无法验证标记与升级。
- M5-06 依赖 M5-02；签名配置可以在 M5-08 完成，但更新器必须先能读取 `publisherName` 与更新源。
- M5-08 依赖 M5-06；发布流水线必须用真实更新元数据验证，不能只构建安装包。
- M5-10 依赖 M5-03～M5-09；干净 VM 验收必须等所有发布链路就绪。

初稿曾把 M5-06 的依赖写成“M5-02、M5-08”，而 M5-08 又依赖 M5-06，形成循环；已改为 M5-06 只依赖 M5-02，签名字段在 M5-08 接入。初稿还把 `publisherName` 写进 M5-01，但证书主题在 M5-08 才确定；已改为 M5-08 写入并校验。

### 9.5 第五遍：验收证据

- 每个任务至少有两类证据：单元/集成、组件/e2e、打包/安装、干净 VM。
- 明确“`pnpm build` 通过”不能证明安装后可用；以已安装应用冒烟与干净 VM 为准。
- 明确“本地更新测试”不能证明公网可匿名下载；发布后必须从公开 URL 重新下载并校验。
- 明确“沙箱单测”不能证明真实命令兼容；必须有真实命令矩阵。
- 明确“签名脚本执行成功”不能证明更新器接受；必须用 `signtool verify` 与一次真实更新流程。

### 9.6 第六遍：范围与一致性

- 长期记忆、macOS/Linux、ARM64、MSIX、遥测、自动回滚、企业分发全部列入非目标，避免重演 M4 的范围蔓延。
- 任务编号、ADR 编号、迁移编号、发布通道与版本号保持一致；M5 从 ADR-0034 起，数据库如无必要不新增迁移。
- 与 M0～M4 的计划风格一致：一个任务一个 PR、实施记录、质量门槛、用户本地验收单独标注。
- UI 任务继续遵守 i18n、设计令牌、浅色/深色截图与“不显示金额”。
- 系统基线写清楚：Windows 11 当前受支持版本（至少 24H2）正式支持，Windows 10 22H2 仅 best-effort；不把 EOL 系统写成正式承诺。

### 9.7 仍需在执行中确认的事项

- S1 已完成：AppContainer 未达到默认可用的兼容性门槛，默认改为受限令牌；受限令牌的网络未隔离已在 ADR-0034 与 M5-05 文案要求中明确。
- S1 的普通用户前提只完成了“未提权的过滤管理员令牌”验证；真正标准用户、Windows 10 与干净 VM 仍由 M5-10 补齐，未通过前不得宣称正式支持。
- 更新源的实际托管商与域名；若对象存储未就绪，使用公开 release-only 仓库过渡。
- 证书类型与申请周期；截止日期前未取得证书时，是否接受 unsigned beta。
- EULA/隐私文本的最终措辞；M5 beta 默认专有许可，M6 开源前替换。
- 安装包体积预算：MinGit 压缩包约 38 MB，最终安装包与安装后体积以 M5-02/M5-03 实测为准；若超出可接受范围，再评估裁剪深度。

## 11. 发布运行手册（Runbook）

### 11.1 发布前

1. 确认 `CHANGELOG.md` 已更新，版本标签与根 `package.json`、桌面包版本一致。
2. 确认签名证书可用、未过期、时间戳服务可访问；更新源凭据可用。
3. 在 `main` 上跑完整质量门槛；在干净 VM 上跑安装/升级/卸载冒烟。
4. 生成候选安装包，校验 asarUnpack、MinGit、许可证与构建信息。
5. 用本地静态源跑一次 `0.1.0 → 0.1.1` 更新演练。

### 11.2 发布

1. 打标签 `v0.1.0`，触发 release workflow。
2. 流水线构建、测试、签名、校验、生成 blockmap 与更新元数据。
3. 上传到公开只读静态源；从公网重新下载安装包与更新元数据，校验 SHA256 与签名。
4. 创建发布说明；标注 beta、Windows x64、按用户安装、签名状态与已知问题。
5. 在干净 VM 上用公网源完成一次真实更新。

### 11.3 发布后

1. 监控更新源下载失败率与错误报告（M5 没有遥测，依赖用户反馈与诊断包）。
2. 保留上一版安装包、blockmap 与更新元数据；紧急撤包时把 `latest.yml` 指回上一版，并发布说明。
3. 若发现沙箱兼容性问题，优先发布“默认更保守的沙箱档位”或修复，不通过关闭沙箱解决。
4. 记录本版构建号、签名指纹、产物哈希与已知问题到 `docs/plan/m5-report.md`（或本文实施记录）。

## 12. 已确认的范围与默认值
