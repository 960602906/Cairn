## 1. 目标

**完成标准**（架构 §26）：用 DeepSeek 完成一个真实的改代码并运行测试的任务，可回退。

具体来说，在一个示例项目上完成以下流程：

1. 用户选择项目目录，配置 DeepSeek 的 Key。
2. 输入任务，例如“修复 `sum` 的 bug 并运行测试”。
3. agent 读文件、改文件、运行测试。写文件和运行命令前弹出审批，用户允许后执行。
4. 测试通过后，用户把工作区回退到这一轮开始之前，文件恢复原样。

M1 接入真实模型和工具，重点是**安全边界一次做对**：路径校验、权限引擎、审批、检查点、命令执行。这些错了会直接损坏用户的文件。

### 1.1 不在 M1 范围内

- 设置页、工具卡片样式、diff 视图、终端输出面板、检查点列表与回退界面、Ollama 接入与能力探测、输入优化：M2。M1 只做完成验收所需的最小界面（M1-16）。
- 上下文压缩、`AGENTS.md`、按块撤销、Skills、MCP、辅助模型：M3。
- 多 Agent、多会话并行、后台命令：M4。
- 命令沙箱、安装包、随应用附带 MinGit：M5。

### 1.2 任务约定

沿用 M0 的约定（m0.md §1.2）：

- 每个任务拆成子任务，一个子任务一个 PR，合并后再开始下一个。
- 每个任务写明依赖、交付物、验收、依据。
- 覆盖率四项不低于 90%。
- 新包只在用到时创建。

M1 另加：

- **真实模型只在本地运行**：CI 只用录制回放（M1-02）。需要真实服务或 Windows 实机的验证，在维护者本机运行，环境见 [`docs/dev/local-testing.md`](../dev/local-testing.md)。任务中以 **[用户本地]** 标出。
- **Key 只从环境变量或凭据服务读取**：不写进仓库、录制文件、日志或 PR 描述。
- **安全相关的代码**（路径校验、权限引擎、命令执行、检查点恢复）的测试必须覆盖失败分支，Windows 特有的情况在 Windows CI 上运行。

## 4. 任务详情

### A. 模型接入

#### M1-01 pi 适配器

- **依据**：ADR-0004、ADR-0021；Runtime §17；S1、S2、S8
- **交付物**
  - 新建 `packages/runtime-pi`，是唯一可引用 `@earendil-works/*` 的包（ESLint 边界规则）。实现 `AgentRuntime` / `RuntimeSession`，`RunEngine`、`RunSupervisor` 不需要改动。
  - pi-agent-core 与 pi-ai 声明为同一精确版本 1.5.0，加 S8 的版本守卫测试。
  - `CanonicalMessage` 与 pi 消息双向转换：文本、推理（含签名、`providerId`）、工具调用与结果、用量。
  - pi 的工具回调接到 `hooks.beforeToolCall` / `hooks.executeTool`，取消信号向下传递。
  - pi 事件映射为 `RuntimeEvent`：`step.started`、`text.delta`、`reasoning.delta`、`message.completed`、`step.completed`、`loop.ended`。被中止或出错的一步不发出 `message.completed`，由 `RunEngine` 保存部分回复（M0 已实现）。
  - `ResolvedModel` → pi 模型定义：DeepSeek 用 pi-ai 内置目录；其他按 `ProviderConfig` 构造，兼容参数由 M1-04 的模板给出。
  - 宿主改用 `runtime-pi`，`FakeRuntime` 保留给测试与 e2e（环境变量切换）。pi 打进宿主产物（S1），附带 `THIRD_PARTY_NOTICES`（ADR-0014）。
- **验收**：用本地 mock 端点（S1 的 mock 服务）跑通一次带工具调用的对话，覆盖中止、401、模型错误；打包后的应用能加载宿主；`check:licenses` 通过。
- **子任务**
  - **M1-01a 包骨架与版本守卫**：`packages/runtime-pi`、依赖边界规则、版本守卫测试。
  - **M1-01b 消息转换**：`CanonicalMessage` ↔ pi 消息，往返测试覆盖三种格式的推理内容与工具调用。
  - **M1-01c 会话与事件映射**：`createSession`、`prompt`、`steer`、`abort`、`exportHistory`；pi 事件 → `RuntimeEvent`；工具回调接到 hooks；用 mock 端点测试。
  - **M1-01d 接入宿主与打包**：宿主按配置选择运行时；Vite 打包 pi；`THIRD_PARTY_NOTICES`；打包冒烟测试。
- **实施记录**
  - M1-01a（已完成）：
    - 新建 `packages/runtime-pi`，依赖 pi-agent-core、pi-ai 1.5.0，可引用 `@nexus/protocol`、`@nexus/core`；在 `eslint.config.js` 的 `ALLOWED_NEXUS_DEPS` 登记。只有它可以引用 pi 的规则在 M0-02 已经存在。
    - `PI_VERSION` 是锁定版本的唯一出处，`pi-version.test.ts` 检查 package.json、`pnpm-lock.yaml` 与实际安装都与它一致。
    - 版本守卫从 S8 移入，并改为读 pnpm 锁文件，另外检查两点：其他工作区包不声明 pi 依赖；每个 pi 包在锁文件 `snapshots` 中只有一份（同一版本、peer 依赖不同时 pnpm 也会装出两份）。
    - 确认 pi 的生产依赖都在 `check:licenses` 的检查范围内，许可证均通过。
  - M1-01b（已完成）：
    - `packages/runtime-pi/src/messages.ts`：`toPiMessages` / `fromPiMessages`，以及 `fromPiUsage`。
    - protocol 增加两个可选字段（向后兼容）：
      - `ReasoningPart.blocks`：原样保存推理块的签名、被隐去的块和多块推理。DeepSeek（openai 格式）靠签名记录回传推理用的字段名 `reasoning_content`，缺了它思考模式下的多轮工具调用会失败（S2）；Anthropic 需要 thinking 签名。
      - `ToolCall.signature`：Gemini 的 thought signature。
    - 只有会话当前模型产生的助手消息才带当前模型的 pi 标识（provider、api、id），pi 据此判断“同一模型”并保留签名；其他模型的消息标为外来（api `nexus-foreign`），pi 会去掉其中的推理与签名。其他提供方的推理在转换时就不发出（Runtime §14）。
    - 工具结果的状态（denied、cancelled、unknown）存入 pi 工具结果的 `details`，可以原样转回。
    - `TokenUsage.inputTokens` 定为含缓存部分。pi 的 `input` 不含缓存，转换时加回。
    - 暂不处理的情况：
      - 图片暂以文字占位，接入 blob 存储后再转换；
      - `summary` 转为带前缀的用户消息；
      - pi 工具调用的 `argumentsError`（参数不是合法 JSON）留给 M1-14b 处理。
    - 测试：
      - 三种格式的助手消息往返不变，并能通过 schema 持久化；
      - 用 pi 自己的 `transformMessages` 验证：同一模型时推理和签名会发给模型，换模型后被去掉；
      - 完整历史（含五种工具结果状态）往返不变。
    - 请求体中确实带上 `reasoning_content`，要在 M1-01c 用 mock 端点验证。
  - M1-01c（已完成）：
    - `PiRuntime`（`id: 'pi'`）基于 pi-agent-core 的 `Agent`：
      - `session.ts`：会话与事件映射；
      - `model.ts`：`ResolvedModel` → pi 模型定义；
      - `errors.ts`：失败分类。
    - 模型：
      - openai 格式且模型 id 在 pi 内置目录中时（DeepSeek），用目录中的兼容参数，地址和限额用配置的值，所以经代理接入时同样生效；其他模型按 `ModelProfile` 构造，兼容参数等 M1-04 的模板给出。
      - 每个会话一个 pi 注册表，Key 只在请求时由闭包提供。
      - pi 的 SDK 重试关闭（`maxRetries: 0`），由 M1-14 统一重试。
    - 工具：
      - `execute` 中依次调用 `hooks.beforeToolCall`、`hooks.executeTool`，取消信号传给工具，结果状态写入 `details`；
      - 按顺序执行，审批也按顺序进行；并行由 M1-05 决定。
    - 历史由会话自己维护：
      - 用户消息（含 steer）用调用方传入的原对象；
      - 出错或被中止的助手消息不进入历史；
      - 空闲时 steer 直接进入历史，随下一次 prompt 发送。
    - 失败按 HTTP 状态归类为新增的错误码，是否可重试以 pi 的判断为准，429、5xx 视为可重试。新增的错误码是 `model.auth_failed`、`rate_limited`、`server_error`、`context_overflow`、`bad_request`、`network_error`，并补了中英文文案。
    - pi 的 `prompt` 抛出时（例如事件监听器抛出），按失败结束本轮，保证恰好一个 `loop.ended`。
    - 测试用 `src/testing/mock-openai.ts`（openai 格式 SSE mock 端点，记录请求），验证了：
      - 工具调用对话的事件顺序与历史；
      - 第二次请求带回 `reasoning_content`（S2）；Key 只出现在请求头；
      - 拒绝工具；从历史恢复后推理带回同一模型；
      - 401 / 429 / 500 / 400 / 连接失败；
      - 流式中、工具执行中、会话信号三种中止；
      - 空闲与运行中的 steer。
    - anthropic、gemini 格式的端到端行为由 M1-02 的录制回放覆盖。
  - M1-01d（已完成）：
    - 宿主按环境变量选择运行时（`agent-host/runtime-select.ts`）：
      - `NEXUS_RUNTIME=pi` 时用 `PiRuntime`，模型由 `NEXUS_MODEL_KIND`、`NEXUS_MODEL_BASE_URL`、`NEXUS_MODEL_ID`、`NEXUS_MODEL_API_KEY`、`NEXUS_MODEL_REASONING` 给出，配置不完整时 `host.init` 失败；
      - 其他情况仍用 FakeRuntime（单元测试、界面开发、端到端测试）。
      - 这只是开发入口：M1-03、M1-04 完成后，模型配置与凭据由主进程经 `host.init` 传入。
    - 打包：pi 及其依赖由 electron-vite 打进宿主产物（只有桌面应用 package.json 中的依赖保持外部），无需改配置。
    - ESLint：桌面应用可以引用 `@nexus/runtime-pi`，渲染进程禁止引用。
    - `scripts/third-party-notices.js`：`build` 后生成 `out/THIRD_PARTY_NOTICES.txt`，列出全部生产依赖（名称、版本、许可证、作者、主页）并附许可证全文；pi 等少数包不带许可证文件，注明“未随包附带”。
    - 冒烟测试先检查声明文件列有 pi，再分别用 FakeRuntime 和 pi 各启动一次；pi 指向本地 mock 端点（`scripts/mock-model.js`），检查请求带 Key、模型正确且为流式，并完成一轮对话。

#### M1-03 凭据服务

- **依据**：ADR-0010；架构 §16.2
- **交付物**
  - 主进程 `CredentialProvider`（`local-key`）：`safeStorage` 加密，存储在应用数据目录（不进 SQLite 的普通表，也不进 `settings.json`）。
  - `credentials.set` / `credentials.delete` / `credentials.status`：渲染进程只能写入和查询是否存在，不能读出。
  - 只在 `host.init` 时把解析好的凭据传给对应会话的宿主；日志脱敏规则覆盖凭据。
  - `safeStorage` 不可用时（Linux 无密钥环）拒绝保存并返回明确错误码（M6 再处理退化方案）。
- **验收**：单元测试用假的加密实现；Windows CI 上用真实 `safeStorage` 存取；e2e 检查渲染进程拿不到明文。
- **子任务**
  - **M1-03a 凭据存储**：`CredentialProvider` 与加密文件格式。
  - **M1-03b IPC 与宿主传递**：三个 IPC 方法；`host.init` 携带凭据；脱敏测试。
- **实施记录**
  - M1-03a（已完成）：
    - `@nexus/core` 增加 `CredentialProvider`、`ResolvedCredential` 与凭据引用的格式（`[A-Za-z0-9._-]`，1～128 个字符）。
    - 主进程 `services/credential-store.ts`（`local-key`）：
      - Key 去掉首尾空白，最长 4096 个字符；
      - 加密后以 base64 存入数据目录的 `credentials.json`（`version` 1，每项记 `kind`、`ciphertext`、`updatedAt`）；
      - 先写临时文件再改名，POSIX 上权限为 0600；
      - `has` 只查是否存在，不解密。
    - 文件无法解析或版本不支持时视为空；下次写入前把原文件改名备份，不覆盖新版本应用写入的数据。

    - 输出：stdout / stderr 经 `ctx.progress` 流式推送（`tool.output.delta`）；交回模型的结果给出退出码（或超时、取消、信号）、耗时，stdout 与 stderr 分开。超出上限（默认 25 000 字符，与 `read_file` 相同；M1-13 按上下文窗口调整）时保留开头和结尾、中间注明省略的字符数；两段都很长时 stderr 至少占四分之一。内存中每段也只保留开头与结尾（`HeadTailBuffer`，`runCommand` 的 `collectOutput: false`），输出很多的命令不会占满内存。
    - 超时前持续 30 秒以上没有输出时，结果中说明命令可能在等待输入（不支持交互），建议使用非交互选项。运行中的界面提示随 M1-16 按 `tool.output.delta` 的间隔显示。
    - 启动失败（`shell.spawn_failed`）转为工具错误；退出码非 0 不算工具失败，输出照常交回模型。
    - `apps/desktop` 加入 koffi 依赖，使其不被打进产物（koffi 按自身位置查找预编译二进制）；THIRD_PARTY_NOTICES 已包含 koffi。
    - 尚未接入宿主：工具流水线接入宿主在 M1-10/11，届时宿主用 `selectShell` 选出 shell 并注册 `run_command`。shell 偏好（`auto` / `cmd`）的设置项随接入一起加入（M1-09a 原计划在本子任务加入，没有使用方，推迟）。
    - 测试：输出格式、截断与预算分配、代理对不被切开、超时与等待输入提示、取消与信号、流式推送、启动失败；在当前平台选出的 shell 上真实执行（Linux CI 为 bash，Windows CI 为 PowerShell）。
