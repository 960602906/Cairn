# Cairn 里程碑 7：记忆与团队协作

> 状态：规划中（2026-11-17）。M0～M6 已实施，`main` 通过三平台 CI；本计划定义 M6 之后的
> 首个正式里程碑：先交付跨会话记忆（M7-01～M7-05），再做团队模板与审查循环（M7-06～M7-09）。
> stable 发布的前置条件（签名、法务、干净 VM 与真实更新演练）是并行轨道，不阻塞 M7，
> 但关闭前不得签发 stable（见 [M6 验收报告](m6-report.md) §7）。
> 上级文档：[架构设计](../architecture.md)；前一阶段：[M6](m6.md)、[M6 验收报告](m6-report.md)。
> 相关设计：[Agent Runtime](../design/agent-runtime.md) §22、[Agent 管理界面](../design/agent-management-ui.md)、
> [多 Agent 协作](../design/multi-agent.md) §15。
> 相关决策：ADR-0019（记忆范围）、ADR-0020（hub-and-spoke 委派）、ADR-0029（自定义 Agent）、
> ADR-0030（多运行委派）、ADR-0031（隔离工作区）。

## 1. 目标

**完成标准**：

1. Agent 能在严格隔离的会话 / 项目 / 全局范围内读取记忆，并通过 `propose`（用户确认后写入）
   或用户显式开启的 `auto` 写入；所有条目对用户可见、可编辑、可删除，并记录来源。
2. 常用的多 Agent 协作方式可以保存为团队模板：至少支持 `review-loop`（maker/checker 多轮审查）
   与固定的 `pipeline`（有依赖关系的阶段），模板与 Agent 一样有版本、草稿、发布与试运行。
3. 记忆与团队功能都有端到端用例、界面截图与文档，覆盖率维持四项 ≥ 95%。

### 1.1 不在本轮范围内

- **插件市场、通用工作流 DAG**：`pipeline` 只执行模板内固定阶段，不做可视化编排引擎。
- **云端记忆、账号体系与跨设备同步**：记忆只存本地，随项目/会话数据一起备份与导出。
- **遥测、崩溃上报**：沿用诊断包；新增记忆内容不得进入诊断包。
- **移动端、Web 版、企业分发与 MSIX**：没有真实需求前不评估。
- **发布通道本身**：签名、公证、法务与真机矩阵由所有者侧并行推进，见 M6 报告 §7。

## 2. 现状与前提

- `AgentDefinition.memory` 字段已存在（`scopes` + `write`）：读取在 M7-02 接入，写入在 M7-03
  接入（`remember` 工具 + `host.memory.remember`）；`write !== 'never'` 的保留警告已随写入实现移除。
- 记忆设计已在 [Agent Runtime](../design/agent-runtime.md#22-记忆m7-01-存储m7-02-读取m7-03-写入m7-04-管理) 定稿：三个范围严格隔离，
  写入默认 `never`，开放后默认 `propose`，条目可见可控并标注来源。
- 团队模板的数据结构已在 [多 Agent 协作](../design/multi-agent.md#15-团队模板后续) 给出
  （`AgentTeam`：`coordinator` / `members` / `pattern` / `pipeline` / `reviewLoop` / `delegation`）；
  现有委派、隔离工作区与 Agent 版本/草稿/试运行机制可直接复用。
- 上下文组装已有压缩、会话要点与 `AGENTS.md` 注入，记忆需要接入同一套预算与顺序，
  不能绕过压缩与限额。

## 3. 任务拆分

### M7-00 质量防线与文档基线（本次交付，约 1 天）

M6 收尾后分支覆盖率距 95% 门槛只剩极小余量，且多步骤归组改动曾导致 E2E 失败。

- 补 `ChatPanel.tsx` 与 `Markdown.tsx` 的分支覆盖（83.33% → 97.10%、88.88% → 92.59%），
  全量分支从 95.01% 升到 95.14%（16937/17802）；后续任务新增分支必须自带测试，继续积累余量。
- 新增多步骤归组 E2E：默认收起、手动展开后保持、等待审批时自动展开。
- 稳定化 M5 报告记录的两个偶发用例：`host-integration` 的崩溃隔离改为按会话查找宿主进程
  （不再按下标猜）；`workspace-service` 的工作区注册断言只比对完整路径，避免临时目录名
  恰好含 `r1` 时误判。
- README、M6 清单与本计划同步；新增本文件。

### M7-01 记忆存储与数据模型（约 0.5 周，已实施）

- 新迁移 `0018_memory-entries`：`memory_entries`（`memory_id`、`scope`、`project_id` /
  `session_id`、`content`、`status`（`proposed` / `active`）、`source_run_id`、
  `source_agent_id`、`created_at`、`updated_at`）。
- 范围约束用数据库与仓储层双重校验：`session` 必须有会话 ID，`project` 必须有项目 ID，
  `global` 不得携带两者；跨项目读取在查询层就不可达。删除会话时会话记忆级联删除。
- 仓储接口 `Storage.memories`：`propose` / `list`（可按状态过滤，顺序为会话、项目、全局）/
  `confirm` / `update` / `delete`。删除是硬删除并返回被删除的条目；`memory.deleted` 等事件
  与 `memory.proposed` 一起在 M7-03 接入。
- 内存与 SQLite 两种实现由同一套契约测试覆盖（范围隔离、空内容、重复 id、事务回滚、级联删除）。

### M7-02 记忆读取与上下文注入（约 0.5～1 周）

- 按 Agent 的 `memory.scopes` 组装：会话记忆 + 当前项目记忆 + 全局记忆，顺序固定、去重。
- 接入现有 token 预算与压缩：记忆有独立上限，超限按更新时间裁剪，并在运行检查器中可见。
- 上下文组装只读 `active` 条目；`proposed` 不进入模型请求。
- 单测覆盖范围隔离（项目 A 的记忆不出现在项目 B）、预算裁剪、与 `AGENTS.md` 的先后顺序。

### M7-03 记忆写入：propose 与 auto（约 0.5 周，已实施）

- 新增内部工具（暂定 `remember`）：模型提交 `{ scope, content }`；`never` 直接拒绝并说明原因。
- `propose`：写入 `proposed` 并弹出确认卡片（复用 `ask_user` 的浮动操作条模式），确认后转
  `active`，拒绝则删除候选；同一轮多次提议逐条处理。
- `auto`：仅在 Agent 显式配置且用户在设置中开启“允许 Agent 自动记忆”时生效，默认关闭；
  自动写入同样记录来源并在界面可撤回。
- 事件：`memory.proposed`、`memory.accepted`、`memory.rejected`、`memory.deleted`（按
  ADR-0005 追加到事件日志，投影到界面）。

### M7-04 记忆管理界面（约 0.5～1 周，已实施）

- 设置页新增“记忆”分类：按范围分组、搜索、编辑、删除；每条显示来源（哪次运行、哪个 Agent、
  时间）与状态。
- 会话内入口：在会话信息面板展示当前会话记忆与项目记忆，支持就地删除。
- 空状态、长内容折叠、删除确认；中英文文案与浅色/深色截图。
- 实施要点：界面读取走新增的 `memory.list`（`Storage.memories.listAll`，只给界面用），
  编辑与删除分别走 `memory.update` / `memory.delete`；删除有会话上下文时发布 `memory.deleted`，
  会话记忆的提议卡片随之消失。设置页与会话面板复用同一个条目卡片，避免两处交互漂移。

### M7-05 隐私、导出与文档（约 0.5 周，已实施）

- 记忆内容属于用户数据：诊断包默认不包含；导出/删除项目数据时一并处理。
- 更新隐私说明、架构文档、CHANGELOG 与设置页说明；补充“记忆与 `AGENTS.md` 的区别”。
- 端到端验收：提议 → 确认 → 下一轮请求包含记忆 → 删除后不再出现；跨项目隔离。
- 实施要点：诊断包的默认摘要本来就只取白名单字段，这次补上“即使勾选包含会话正文也不导出
  记忆正文”（只留长度）；会话与项目删除沿用外键级联，记忆随之一并删除。设置页补充“记忆与
  `AGENTS.md` 的区别”，端到端用例覆盖提议 → 确认 → 注入 → 删除与跨项目隔离。

### M7-06 团队模板数据模型（约 0.5 周，已实施）

- `AgentTeam` schema（见多 Agent 协作 §15）进入协议与存储：版本、草稿、发布、归档。
- 校验：`coordinator` 必须存在且可委派；`members` 去重；`reviewLoop.maxRounds` 有上限；
  `pipeline` 的 `dependsOn` 必须构成 DAG 且引用同一模板内的阶段。
- 模板与 Agent 共用版本/草稿/试运行机制，不复制一套。
- 实施要点：`TeamDraft` / `AgentTeam` 进入协议，存储新增 `agent_teams` 与
  `agent_team_versions`（迁移 0019），`AgentTeamStore` 与 `AgentStore` 形状一致；校验在
  `@cairn/core` 的 `validateAgentTeam`，另给 `teamPipelineOrder` 计算依赖在前的拓扑顺序，
  供 M7-08 执行。主控未允许某成员只给警告，运行时仍会再收敛一次。

### M7-07 审查循环（约 1 周，已实施）

- `review-loop`：maker 产出 → checker 审查 → 未通过则回传意见给 maker，最多 `maxRounds`；
  每轮一个子运行，父运行只负责编排与汇总。
- 终止条件：通过、轮次用尽、任一子运行失败/被停止、预算或限流触发；每种结局在界面与事件里
  有明确文案。
- 复用现有委派限额继承与隔离工作区；子运行仍只读（沿用 M4 的边界）。
- 实施要点：编排在 `@cairn/core` 的 `runReviewLoop`（纯依赖注入，结局为
  `passed` / `exhausted` / `failed` / `stopped` / `limit_reached`），宿主登记 `review_loop`
  工具并复用 `runDelegation` 创建每轮的 maker / checker 子运行；两者都必须是只读 Agent，
  写入类目标直接拒绝。轮次会按本轮剩余子运行名额收缩，避免中途被每轮上限截断；checker
  通过 `outputSchema` 返回 `{verdict, feedback}`，缺判定按“未通过”处理。事件为
  `team.review.round` / `team.review.completed`，投影成 `view.reviewLoops`，对话里显示审查
  循环卡片（轮次、判定、结局）。maker 第一轮就失败时完成事件仍会补出这段循环。

### M7-08 pipeline 模板（约 1 周，已实施）

- 按 `dependsOn` 拓扑执行固定阶段；无依赖的阶段可并发，受现有并发上限约束。
- 失败传播：某阶段失败时默认停止后续阶段并汇总原因；已完成阶段的产物保留。
- 界面显示阶段进度（复用计划进度卡的图形与色调）；不做用户自定义 DAG 编辑器。
- 实施要点：编排在 `@cairn/core` 的 `runTeamPipeline`：用 `teamPipelineOrder` 得到依赖在前的
  顺序，按“就绪阶段”分波执行，同波并发不超过 `maxParallel`（受委派策略钳位）；阶段可以是
  任意只读 Agent，复用 `runDelegation` 的限额与边界。任一阶段失败/被停止/触及限额时，
  同波已开始的阶段照常完成，其余阶段记为跳过。宿主登记 `run_pipeline` 工具，校验阶段 id
  唯一、依赖存在且无环，并按本轮剩余子运行名额拒绝超发。事件为 `team.pipeline.stage` /
  `team.pipeline.completed`（带 `skipped`），投影成 `view.pipelineRuns`，对话里显示流水线
  进度卡片。阶段 id 会写进任务书上下文，便于区分同名目标的阶段。

### M7-09 试运行与验收（约 0.5 周）

- 团队模板试运行：在草稿状态开一次隐藏会话（复用 Agent 试运行），默认只读。
- 端到端：从模板选择到 review-loop 完成；pipeline 失败传播；模板版本回退后行为一致。
- 质量门槛：四项覆盖率 ≥ 95%，`format` / `typecheck` / `lint` / `i18n` / e2e / smoke 全绿；
  更新 CHANGELOG 与验收报告。

## 4. 顺序与依赖

```
M7-00（质量防线）
  └─ M7-01 → M7-02 → M7-03 → M7-04 → M7-05
                                   └─ M7-06 → M7-07 ─┐
                                              M7-08 ─┴─ M7-09
```

- M7-01～M7-03 是记忆的最小闭环，先于界面与文档。
- M7-06 的模板模型可以与 M7-04/M7-05 并行，但审查循环必须等模板能发布后再做。
- 每个任务独立 PR、DCO 签名，界面改动附浅色/深色截图。

## 5. 验收与测试矩阵

| 门槛 | 要求 |
|---|---|
| 单测 | 记忆范围隔离、预算裁剪、提议/确认/拒绝、模板校验（DAG、去重、上限） |
| 集成 | 事件日志 → 投影 → 界面；委派与审查循环的终止条件 |
| 组件 | 记忆管理页、确认卡片、团队模板编辑器、阶段进度卡 |
| e2e | 记忆提议→确认→注入→删除；review-loop 完整跑通；pipeline 失败传播 |
| 隐私 | 诊断包与导出不包含记忆内容；删除项目会删除对应记忆 |
| 覆盖率 | 四项 ≥ 95%，新增代码不得依赖门槛余量 |

## 6. 风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| 记忆把无关上下文带进请求 | 行为不可预测、token 浪费 | 三个范围强隔离；预算上限与裁剪；运行检查器可见 |
| 自动记忆写入用户不希望保留的内容 | 隐私与信任问题 | 默认 `never`；`propose` 需确认；`auto` 需显式开关且可撤回 |
| 审查循环无限来回 | 成本失控 | `maxRounds` 硬上限 + 预算/限流照常生效 |
| 团队模板范围蔓延成工作流引擎 | 进度失控 | 只做固定模板与 `pipeline`，不做可视化 DAG 编辑器 |
| 覆盖率门槛被新增分支挤破 | CI 反复红 | M7-00 先把余量拉回安全区，每个任务自带测试 |
| stable 阻塞项继续悬置 | 无法发布 | 并行轨道推进；M7 完成不等于 stable 就绪，发布说明继续标注 unsigned beta |
