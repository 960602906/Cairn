## 1. 目标

**完成标准**（架构 §26）：多任务并行互不干扰。

具体来说：

1. 主 Agent 可以通过 `delegate` 把只读子任务交给 `builtin.explorer`、`builtin.reviewer` 等子 Agent；父运行等待子运行，拿到结构化结果后继续，不把子运行的完整对话塞回父上下文。
2. 同一轮可以并行派出多个只读子运行；父运行在 `awaiting_children` 期间不阻塞其他会话，子运行的 token、时长与步骤计入父运行预算，父运行达到限额时子运行一起停止。
3. 写入类子 Agent 在隔离工作区中运行，改动以“改动集”呈现；用户可以按文件接受、拒绝或手动选择冲突版本，合并前创建检查点，合并可以回退。
4. 活动中心聚合所有会话的待审批事项、运行中任务与最近完成；侧栏显示待审批角标；应用不在前台时可以发送系统通知，点击通知回到对应会话。
5. 检查器可以看到运行树（父运行 → 子运行 → 轮次 → 步骤 → 工具调用）、最近一次模型调用的完整上下文、按 Agent 分组的用量与生效的权限/限额/Agent 版本。
6. Agent 编辑器可以用当前草稿试运行，草稿不需要发布；试运行默认只读，不进入正常会话列表，改动仍可回退。
7. 至少 3 个会话可以同时运行；事件、审批、取消、改动记录严格按会话隔离，空闲宿主按时回收。
8. 质量门槛：四项覆盖率不低于 95%；`pnpm format:check`、`pnpm typecheck`、`pnpm lint`、`pnpm check:i18n`、`pnpm check:licenses`、`pnpm test:coverage`、`pnpm build`、`pnpm e2e`、`pnpm smoke`、`$env:CAIRN_PERF='1'; pnpm test:perf` 全部通过（Ubuntu CI 用 `CAIRN_PERF=1 pnpm test:perf`）；Windows 与 Ubuntu CI 同时通过。

### 1.1 不在本轮范围内

- 跨会话长期记忆（ADR-0019）：M4 只保留 Agent 定义中的 `memory` 字段，不实现存储、提取、注入或管理界面。记忆需要独立的隐私边界、提取策略、检索质量评估与嵌入模型选型，放在 M4 之后的独立里程碑。
- 团队模板、审查循环、工作流 DAG（MA-4/MA-5）：M4 默认单层委派，`maxDepth` 可配到 2，全局硬上限 3；不做审查循环与团队模板。
- 命令沙箱、安装包、签名、随应用附带 MinGit：M5。
- macOS、Linux 正式适配与打包：M6；M4 仍以 Windows 首发，Ubuntu 只作为 CI 与开发验证环境。
- 任何金额、费用、预算显示：不做（视觉规范 §10）；只显示 token 数。
- 更多模型提供方：现有 OpenAI / Anthropic / Gemini 三种线路格式与任意 Base URL 已覆盖接入需求；M4 不单列“新增厂商”任务，只在需要时补配置模板。
- 后台命令：作为 M4 收尾的可选任务（M4-14），不阻塞 M4 完成标准；如果 M4-00 预研不通过，直接移出 M4。

### 1.2 任务约定

沿用 M3 的约定：

- 一个子任务一个 PR，标题形如 `feat(core): 多运行调度 [M4-01]`；合并后再开始下一个。跨任务的共享接线在 §6 单独列出，避免两个任务互相等待。
- 每个 PR 同时更新本文：§4 的“状态”一行，以及对应任务下的“实施记录”（做了什么、与计划的差异及原因）。
- 提交前在仓库根目录运行：`pnpm format:check`、`pnpm typecheck`、`pnpm lint`、`node scripts/check-i18n.js`、`pnpm test:coverage`（四项覆盖率不低于 95%）。改到桌面端时再运行 `apps/desktop` 下的 `pnpm build` 与 `pnpm e2e`；最终收尾再运行 `pnpm smoke` 与 `CAIRN_PERF=1 pnpm test:perf`。
- 界面文案全部走 i18n（ADR-0013），`packages/i18n/locales/zh-CN` 与 `en-US` 同时补齐；lint 规则 `cairn/no-literal-ui-text` 不允许在组件里写死文字。
- 组件只用设计令牌（`styles/tokens.css`）的颜色；界面 PR 附浅色、深色截图。
- 新依赖取最新稳定版，通过许可证检查（ADR-0014，`scripts/license-exceptions.json`）；工作区内新包要同时加入 `apps/desktop` 的依赖和 `electron.vite.config.ts` 的 `workspacePackages`，否则宿主打包会失败。
- 新的协议类型、事件、RPC 写在 `packages/protocol`（zod）；主进程实现在 `apps/desktop/src/main/services/`，经 `renderer-gateway.ts` 暴露给渲染进程；`packages/core` 不引用 DOM、Node、Electron 类型。
- API Key、MCP 令牌等凭据只经过凭据服务（ADR-0010，`safeStorage`），不写进配置、日志、事件、诊断包、PR 描述。
- 涉及新的架构决定时补 ADR（编号从 0030 起，见 §2.3），在任务的“实施记录”里引用。
- 子运行的权限永远不能超过父运行；子运行的审批必须同时出现在父运行的委派卡片与活动中心；任何“本会话始终允许”仍然受子 Agent 自身权限约束。
- 新增事件与可选字段保持向后兼容；如果改变已有字段的含义或必填性，提升 `EVENT_SCHEMA_VERSION` 并补迁移/恢复测试。

## 2. 范围裁决与前置结论

### 2.1 为什么以 MA-1/2/3 为主干

`docs/design/multi-agent.md` 已经确认了以父运行为中心的委派模型（ADR-0020），并把交付拆成：

| 阶段 | 内容 | 原计划 |
|---|---|---|
| MA-1 | 串行只读委派、`delegate` 工具、委派卡片、运行树、预算与权限收敛 | M4 |
| MA-2 | 并行只读、代码审查 Agent、合并审批显示 | M4 |
| MA-3 | 共享写入（串行）、隔离工作区、改动集审阅与合并、测试补全 Agent | M4 |
| MA-4 | 审查循环与团队模板 | M4 之后 |
| MA-5 | 工作流 DAG | 自动化阶段 |

架构 §26 的 M4 完成标准是“多任务并行互不干扰”，并明确列出了 git worktree 隔离。没有 MA-3，写入类子 Agent 无法安全并行，M4 的完成标准不成立。因此 M4 以 MA-1 → MA-2 → MA-3 为主线，活动中心、运行树/检查器、试运行作为让多 Agent 可用的配套任务，而不是另一条独立主线。

旧的 `m4.md` 草稿把“运行树 + 委派协议”压成一个任务，把长期记忆放进 M4，又漏掉 worktree 隔离，无法作为执行计划。本版重写后，任务之间的依赖、验收与范围边界以本文为准。

### 2.2 现有基础与缺口

| 能力 | 现状 | M4 动作 |
|---|---|---|
| 多会话并行 | `session-manager` 已支持最多 3 个宿主、排队、空闲回收 | 只做并发隔离与真实负载硬化（M4-13），不重写 |
| 父子运行 | 事件有 `parentRunId`，状态机已有 `awaiting_children`，`run.delegated` / `run.child.completed` 只有占位字段 | 扩成完整的多运行调度与委派协议（M4-01/02） |
| 权限 | 工具类别已有 `delegate`，默认放行；权限引擎支持规则与强制拦截 | 增加父子权限交集、委派审批与子运行归属（M4-03） |
| 检查点 | 影子 Git 仓库按项目共享、按会话分引用；支持 `checkpoint` / `diff` / `restore` | 作为隔离工作区的基础（M4-08） |
| 改动记录 | `file_changes` + `hunks` 已支持按文件/按块撤销与 diff | 增加改动集、合并与冲突（M4-09/10） |
| Agent | 定义、版本、草稿/发布、工具选择、Skills、MCP 已落地；只有 `builtin.coder` | 增加 `DelegationPolicy` 与三个内置专业 Agent（M4-02/11） |
| 运行树/检查器 | 没有运行树视图，也没有上下文快照 | 新增投影、快照与检查器（M4-04/05） |
| 活动中心 | 侧栏“活动”入口仍隐藏，审批服务只有按会话查询 | 新增跨会话聚合、角标与系统通知（M4-06/07） |
| 试运行 | Agent 编辑器没有试运行入口；“记忆”分区显示“即将推出” | 新增草稿试运行面板（M4-12） |
| 长期记忆 | 只有 `AgentMemoryPolicy` 字段 | 保持预留，不在 M4 实现 |
| 后台命令 | `run_command` 结束时会结束它启动的后台进程 | 可选任务（M4-14），不阻塞完成标准 |

## 3. 技术选型

| 用途 | 选择 | 说明 |
|---|---|---|
| 多运行调度 | 扩展现有 `RunSupervisor`（`packages/core`） | 同一会话宿主内管理 N 个运行；每个运行有自己的 `RunEngine`、运行时会话、模型、限额与取消信号，不共享对话历史 |
| 子运行运行时 | 每个子运行使用独立的 `AgentRuntime.createSession` | 复用现有 `AgentRuntime` 接口；不引入新的运行时依赖。子运行使用自己的模型与凭据解析结果 |
| 隔离工作区 | 影子仓库 + `git worktree add --detach` | 以委派时刻的检查点提交为基线；不复制 `node_modules`，用 junction / symlink 共享只读依赖；失败时回退到从影子提交导出到独立目录 |
| 改动集 | 复用 `change-service` 与 jsdiff | 新增 `change_sets` / `change_set_files` 表；改动集保存基线提交、文件列表、diff 与状态 |
| 活动中心 | 主进程聚合 + Electron `Notification` | 不引入新依赖；审批服务增加全局索引，通知只在窗口不在前台时发送 |
| 运行树/检查器 | 事件投影 + 新 `run_snapshots` 表 | 运行树从事件日志重建；上下文快照在每次模型调用前记录，按运行保留最近 N 份 |
| 试运行 | 现有会话/宿主 + `trial` 标记 | 试运行是普通会话的一种，使用草稿 Agent 定义；默认只读；不进入正常会话列表 |
| 后台命令（可选） | 现有 `@cairn/shell` + 进程树管理 | 新增长期进程服务、输出缓冲与停止接口；不引入新依赖 |
| 测试 | 现有 Vitest / Playwright / FakeRuntime / mock 模型 | 多运行用 FakeRuntime 做确定性测试；真实 Git worktree 在 Windows CI 与本地验证 |

## 5. 任务详情

### M4-00 预研与文档基线

- **目的**：在改动运行时与存储之前，先把 M4 的四个高风险假设验证掉，避免后续任务建立在猜测上。
- **预研项**
  - **S1 同一宿主多运行**：在同一 `utilityProcess` 中创建 2～3 个 `PiRuntime` 会话，测量内存、CPU、事件隔离、中止与模型切换；确认 `RunSupervisor` 可以按运行创建独立的 `RunEngine` 与运行时会话。
  - **S2 隔离工作区**：在 Windows 与 Ubuntu 上用影子仓库的检查点提交执行 `git worktree add --detach`；验证非 Git 项目、未提交改动、嵌套仓库、`node_modules` junction、路径长度与清理。失败时确定“从影子提交导出到独立目录”的回退方案。
  - **S3 活动中心通知**：验证 Electron `Notification`、窗口焦点判断、点击通知聚焦会话、系统勿扰模式下的行为；确认通知内容不包含消息正文与凭据。
  - **S4 后台命令**（可选）：验证现有 `@cairn/shell` 能否在应用退出时可靠结束子进程树；不能则 M4-14 直接移出 M4。
- **交付物**：`docs/plan/m4-spikes.md`（每项：假设、步骤、测量数据、结论、go/no-go）；`docs/adr/0030-multi-run-delegation.md`、`docs/adr/0031-isolated-workspaces.md`、`docs/adr/0032-activity-center.md` 的草稿；必要时更新 ADR-0003 / ADR-0008 / ADR-0020 的“后续影响”。ADR-0033 由 M4-04 起草并定稿。
- **验收**：每项预研有可复现的脚本或测试；结论明确到“采用 / 回退 / 移出 M4”；不写产品代码。
- **依赖**：无。
- **风险**：S1 失败会让 M4-01 改为“每个子运行一个独立宿主”，成本和事件接线都会变化；S2 失败会让 M4-08 改为复制式工作区，磁盘占用与性能需要重新评估。
- **实施记录**
  - M4-00：
    - 新增 `spikes/m4`（不进入 pnpm workspace）：`src/s1-multi-run.test.ts`、`src/s2-worktree.test.ts`、`src/s3-notification-policy.mjs`、`src/s3-policy.test.ts`、`src/s3-notification.mjs`、`src/s4-background-command.test.ts`、`src/fixtures/long-running.mjs`；根目录新增 `pnpm spike:m4`，CI 新增 `.github/workflows/spike-m4.yml`（Windows + Ubuntu）。

    - ADR 草稿：`0030-multi-run-delegation.md`、`0031-isolated-workspaces.md`、`0032-activity-center.md`，并在 ADR README 登记为“提议”；ADR-0003 / 0008 / 0020 的“后果”补充 M4 的落地边界。

### M4-01 多运行调度与父子运行生命周期

- **目的**：把 `RunSupervisor` 从“同一时间一个运行”扩展为“同一会话内多个运行”，为委派、运行树与子运行审批提供底座。
- **设计依据**：Runtime §4、§5、§10.1、§16；[多 Agent 协作](../design/multi-agent.md) §4、§12；ADR-0020、ADR-0030。
- **交付物**
  - `RunSupervisor` 支持 N 个运行：`createRun` 可带 `parentRunId`；`getRun`、按父运行列出子运行、运行结束时清理；同一会话内运行 id 全局唯一。
  - 每个运行有独立的 `RunEngine`、运行时会话、模型、系统提示词、工具、检查点与中止信号；`RunSupervisorOptions` 改为按运行创建上下文（`createRunContext`），不再假设“一个 supervisor 一个模型”。
  - 父运行在等待子运行时进入 `awaiting_children`；子运行全部结束后回到 `tooling`，再进入 `thinking`，结果作为工具结果回填父运行。
  - 取消信号树：父运行中止时所有子运行中止；子运行中止时父运行继续，子运行结果标记为 `aborted`；宿主关闭时全部中止。
  - 预算继承：子运行限额取“子 Agent 限额、任务书预算、父运行剩余预算 × `childBudgetShare`”三者的最小值；子运行消耗计入父运行本轮消耗。
  - 协议与事件：`run.created` 的信封带 `parentRunId`；`run.delegated` 与 `run.child.completed` 的信封带 `parentRunId`，载荷扩展为完整结果（任务书摘要、工作区方式、结果状态、用量、改动集 id）。
  - 存储：运行仍以事件日志为准；`agent_runs` 表已有 `parent_run_id` 但当前未写入，M4 不依赖它。运行树走事件投影；只有投影性能不足时才在 M4-04 评估物化表，不提前新增迁移。
- **验收**
  - core 单测（FakeRuntime）：父运行创建 2 个子运行并等待；子运行完成后父运行继续；父运行中止时子运行全部中止；子运行单独中止不影响父运行；限额继承与用量回填正确；运行清理后 `getRun` 返回 undefined。
  - 宿主集成测试：同一宿主内两个运行的事件都带正确的 `runId` / `parentRunId`，事件顺序稳定，没有串运行。
  - 运行中恢复：父运行与子运行都按 Runtime §13.2 处理为中断，不重复执行已完成的工具。
- **依赖**：M4-00。
- **风险**：同一宿主的多运行时实例可能共享 pi 的全局状态；S1 不通过时改用独立宿主，需要调整取消与预算实现。
- **实施记录**
  - M4-01：
    - `RunSupervisor`（`packages/core/src/run-supervisor.ts`）改为多运行调度：`createRun` 支持 `parentRunId`；新增 `listRuns` / `listChildren`；新增 `maxRuns` 上限与 `DuplicateRun` / `ParentNotFound` 错误码；运行 id 会话内唯一，`dispose` 后从管理器清理。`RunSupervisorOptions` 增加 `createRunContext`（按运行创建运行时、模型、限额、系统提示词、工具、检查点与重试策略），全局配置作为回退，不再假设“一个 supervisor 一个模型”。
    - 取消树：`abort` 先级联中止所有子运行再中止自身；`dispose` 级联释放子运行；宿主信号 `abort` 仍作用于全部运行。`AgentRunHandle` 新增 `awaitChildren` / `setAwaitingChildren` / `recordChildUsage` / `remainingLimits` / `parentRunId`。

    - 与计划的差异：编辑器中“按父运行列出子运行”落在 `listChildren`；`ParentNotFound` 错误码已定义但当前 `createRun` 不强制校验父运行存在（委派接线在 M4-02 定稿后启用），本任务只保证取消与清理的级联。宿主集成事件归属由既有 `session-manager` 覆盖，未重复新增测试。

### M4-02 委派协议与 `delegate` 工具

- **目的**：让父 Agent 通过正常的工具流水线发起委派，而不是绕过权限、审批与事件记录。
- **设计依据**：[多 Agent 协作](../design/multi-agent.md) §5、§6、§10；Runtime §16；ADR-0016、ADR-0020。
- **交付物**
  - 协议：`AgentDefinition` 增加 `delegation: DelegationPolicy`（`enabled`、`allowedAgents`、`maxDepth`、`maxChildrenPerTurn`、`maxParallel`、`childBudgetShare`、`defaultWorkspace`、`mergeReview`）；`TaskBrief`、`DelegateInput`、`DelegateResult`、`DelegationValidation`。
  - 核心：`validateDelegation`（目标必须已发布且在 `allowedAgents` 中；深度、并发、循环委派、重复任务检查）；`delegate` 工具定义（JSON Schema、说明中列出可委派 Agent 的名称与描述）；委派工具在 Agent 未启用委派时不注册。
  - 宿主：`delegate` 工具走完整流水线（权限 → 审批 → 创建子运行 → 等待 → 结果）；父运行等待期间不阻塞同一会话的其他运行；`needs_input` 以结构化结果返回父运行，由父运行决定是否询问用户。
  - 主进程：`host.delegate` 解析目标 Agent 的已发布版本、模型、凭据、工具、Skills、MCP 与工作区方式；子运行的凭据只在宿主内存中使用，不写入事件与日志。
  - 事件：`run.delegated`（`childRunId`、目标 Agent、任务书摘要、工作区方式；父运行 id 在信封里）；`run.child.completed`（`completed` / `failed` / `aborted` / `needs_input` / `limit_reached`、摘要、用量、改动集 id、问题）。
  - 结果校验：子运行的最终回复按 `outputSchema` 解析；失败时让子运行修正一次，仍失败则把原文作为 `summary` 返回，不阻塞父运行。
  - 界面：委派卡片的最小数据契约（M4-05 实现视图）。
- **验收**
  - 协议与核心单测：合法/非法目标、`allowedAgents`、深度 1/2/3、循环委派、重复任务、并发上限、任务书大小上限。
  - 宿主集成测试（FakeRuntime）：父运行调用 `delegate` → 子运行执行 → 父运行拿到结构化结果；未启用委派时工具不可见；目标 Agent 不在 `allowedAgents` 中时返回权限错误而不是创建子运行。
  - 凭据测试：子运行的模型 Key 不出现在事件、日志、错误消息与诊断包。
- **依赖**：M4-01。
- **风险**：如果目标 Agent 使用不同模型，宿主需要为子运行创建第二个运行时；S1 的测量数据决定是否允许同一宿主内并存多个模型上下文。
- **实施记录**
  - M4-02：
    - 协议（`packages/protocol/src/delegation.ts`）：新增 `DelegationPolicy`（`enabled`、`allowedAgents`、`maxDepth`、`maxChildrenPerTurn`、`maxParallel`、`childBudgetShare`、`defaultWorkspace`、`mergeReview`）、`TaskBrief`、`DelegateInput`、`DelegateResult`、`DelegateUsage`、`DelegationIssue` / `DelegationValidation`，以及全局硬上限与默认值；`AgentDefinition.delegation` 保持可选，兼容没有该字段的旧定义。
    - 核心（`packages/core/src/delegation.ts`）：`resolveDelegationPolicy` 补默认值并钳到全局上限；`validateDelegation` 检查启用、`allowedAgents`、已发布、深度（含链路沿用上限）、循环、重复任务（第二次警告、第三次拒绝）、每轮子运行数、并行数、任务书大小、预算与工作区；`delegateToolSpec` 在说明中列出目标名称与描述并标为可并行；`DelegationSession` 按轮重置计数与重复记录；`runDelegation` 创建子运行、进入 `awaiting_children`、发送任务书、解析 JSON 信封、结构不合规时修正一次、回填用量并发出 `run.delegated` / `run.child.completed`。
    - 运行调度：`CreateRunInput` 增加按运行 `context`；`AgentRunHandle` 增加 `emitEvent`（委派事件使用父运行信封）；`ToolDefinition.parallel` 允许 `delegate` 与其他只读工具并行。

### M4-03 权限收敛、预算继承与取消传播

- **目的**：保证子 Agent 不能获得比父运行更多的权限，预算与取消行为可预测。
- **设计依据**：[多 Agent 协作](../design/multi-agent.md) §9、§10、§11；Runtime §10.1、§10.3；ADR-0007、ADR-0020。
- **交付物**
  - 有效权限 = 子 Agent 定义 ∩ 父运行当前权限 ∩ 委派策略额外限制；强制拦截规则对所有运行同样生效；计划模式下父运行只读时子运行也只能只读。委派给只读 Agent 默认允许，委派给写入/执行类 Agent 默认询问（在现有 `delegate` 类别默认值之上按目标 Agent 收紧）。
  - 审批归属：每个审批请求带 `sessionId`、`runId`、`parentRunId`、`agent`；父运行对话的委派卡片与活动中心都能看到；`allow_session` 对同一会话的子运行生效，但仍受子 Agent 权限限制。
  - 预算：子运行限额计算、父运行剩余预算、`childBudgetShare`、并行分派前的最大消耗估算；子运行 token / 时长 / 步骤计入父运行；父运行达到限额时所有子运行停止并返回 `limit_reached`。
  - 取消：父运行中止时子运行中止；子运行中止时父运行继续；宿主崩溃时同一会话父子运行都中断，未完成子运行标记为“结果未知”；隔离工作区中的改动集保留。
  - 事件：`run.state.changed` 的父子状态转换、`approval.requested` 的归属字段、`turn.limit_reached` 的子运行汇总。
- **验收**
  - 权限矩阵单测：只读父 + 写入子、写入父 + 只读子、计划模式、强制拦截、第三方 MCP 工具、`allow_session`。
  - 预算单测：子运行限额取最小值；父运行剩余预算不足时拒绝委派；并行分派前的估算；父运行达到限额时子运行停止。
  - 取消集成测试：父中止、子中止、宿主关闭、崩溃恢复；隔离工作区中的改动集仍可审阅。
- **依赖**：M4-01、M4-02。
- **风险**：审批的“本会话始终允许”与子 Agent 权限的交集容易实现错；用表驱动测试覆盖所有组合。
- **实施记录**
  - M4-03：
    - 权限交集（`packages/core/src/tool-pipeline.ts`）：新增 `combinePermissionDecisions`（`deny` > `ask` > `allow`，同为 `ask` 时合并 `reasonCode` / `matchedRuleIds`）；`ToolPipelineOptions.restriction` 让子运行的每次调用再经过父运行的 `PermissionGate`，取更严格的结果，拒绝与审批载荷都使用交集后的判定。
    - 权限判定（`packages/core/src/permissions.ts`、`apps/desktop/src/agent-host/host.ts`）：新增 `PermissionReasonCode.DelegationTarget`；宿主按 `host.delegate.targets` 返回的目标权限模式登记 `delegate` 审批守卫，只读目标默认放行，写入/执行类目标默认询问。根运行与子运行共用同一守卫；子运行流水线以父运行权限门作为 `restriction`，计划模式与强制拦截因此同样约束子运行；嵌套委派再用 `combinePermissionGates` 把“父运行限制 ∩ 当前子 Agent 权限”作为下一层上限，整条祖先链都生效；`allow_session` 规则只写入当前流水线的规则集，仍受自身 Agent 权限与父运行上限约束。
    - 审批归属（`packages/protocol/src/contracts/host-main.ts`、`apps/desktop/src/agent-host/approval-gate.ts`）：`HostApprovalRequest` 增加 `runId`、`parentRunId`、`agent`；会话仍由主进程按宿主注入，审批服务与活动中心可直接按会话/运行/父运行归属。`host.delegate.targets` 的目标信息增加 `permissions`。
    - 预算（`packages/core/src/delegation.ts`）：`validateDelegation` 在父运行任一剩余限额为 0 时拒绝分派（即使任务书没有预算）；`run.delegated` 载荷增加 `budget`（实际子运行限额，供界面估算）；子运行用量回填后若父运行已到限额，`run.child.completed` 状态记为 `limit_reached`，并中止同一父运行下的其他子运行。
    - 取消：沿用 M4-01 的取消树（父中止级联、子中止独立、`shutdown` 中止全部运行）；本任务补齐宿主委派链路上的父子 id 与预算字段，未改变取消语义。
    - 协议兼容：`HostApprovalRequest` 的新字段只用于宿主与主进程之间的内部 RPC，两端随应用同版本发布；事件只新增可选 `budget`，未提升 `EVENT_SCHEMA_VERSION`。
    - 测试：新增权限交集矩阵、父运行 `restriction` 的允许/询问/拒绝、委派目标审批、子运行审批归属、只读父运行限制写入子 Agent、嵌套委派继承祖先权限、父运行零预算拒绝分派、零预算中止同级子运行等用例；全量测试 2582 通过（19 跳过）。
    - 验证：`npx tsc -b`、`eslint .`、`prettier --check .`、`check-i18n`、`check-licenses` 通过；覆盖率 statements 97.49 / branches 95.04 / functions 96.74 / lines 98.5，四项均 ≥ 95%。

### M4-04 运行树与检查器后端

- **目的**：让用户能看清“谁在做什么、模型实际看到了什么、为什么停下来”，这是多 Agent 可调试的前提。
- **设计依据**：管理界面 §8.1、§8.2；Runtime §12、§13、§15；ADR-0005、ADR-0033。
- **交付物**
  - 运行树投影：从事件日志重建父子运行、轮次、步骤、工具调用、审批、用量与状态；`run.inspect` RPC 返回 `RunTree`（根运行、节点、当前状态、用量、耗时）。
  - 上下文快照：每次调用模型前记录系统提示词各部分、加载的 Skills、工具定义、历史与压缩摘要的估算 token；新迁移 `0011-run-snapshots`；每个运行保留最近 20 份，单份有大小上限。
  - 用量：按运行、按 Agent 分组；父运行汇总子运行；模型调用次数、工具调用次数、token、时长；不显示金额。
  - 生效设置：Agent 版本、权限规则、限额、工作区路径（脱敏为项目相对路径或 `~`）、模型。
  - 脱敏：快照中不出现 API Key、MCP 令牌、用户主目录真实路径；复用诊断包的脱敏函数。
  - ADR-0033：记录快照字段、保留期限、脱敏规则与访问边界；在 M4-04 内起草并定稿。
- **验收**
  - 投影单测：单运行、父子运行、并行子运行、失败/中止、压缩后历史；节点顺序稳定；1000 条事件的投影性能可接受。
  - 快照单测：字段完整、大小截断、保留数量、脱敏；没有凭据。
  - `run.inspect` RPC 集成测试：运行中增量、运行结束后完整、恢复后仍可读。
- **依赖**：M4-01、M4-02。
- **风险**：快照体积增长过快；用保留数量、单份上限与懒加载控制。

### M4-08 隔离工作区服务

- **目的**：让写入类子 Agent 在独立工作区中修改文件，避免与主工作区或其他子 Agent 互相覆盖。
- **设计依据**：[多 Agent 协作](../design/multi-agent.md) §7；ADR-0008、ADR-0031。
- **交付物**
  - `WorkspaceService`：`createIsolated({ projectPath, baseCommit, sessionId, runId })` → 隔离工作区路径；`cleanup(runId)`；`list()`；磁盘配额与并发上限。
  - 基于影子仓库的检查点提交执行 `git worktree add --detach <path> <commit>`；非 Git 项目或 worktree 失败时，从影子提交导出到独立目录。
  - `node_modules`、`.venv` 等依赖目录以只读 junction / symlink 共享；不复制大型依赖；嵌套仓库与检查点排除项不进入工作区。
  - 路径：`%APPDATA%/Cairn/worktrees/<sessionId>/<runId>`（macOS/Linux 对应应用数据目录）；Windows 长路径与清理失败的处理。
  - 宿主：子运行 `workspace.path` 指向隔离工作区；路径校验、检查点与改动记录都以该路径为根；主工作区不被写入。
  - 共享写入：`shared` 方式只允许同一时刻一个写入子运行，由会话级工作区锁保证；`isolated` 方式可以并行。
  - 事件：不新增 `workspace.*` 事件。工作区方式与相对路径写入 `run.delegated` 载荷，创建与清理结果写日志；`run.child.completed` 带改动集 id。事件流仍以运行生命周期为主，临时目录不成为可重放状态。
- **验收**
  - 真实 Git 集成测试（Windows + Ubuntu）：Git 仓库、非 Git 目录、有未提交改动、嵌套仓库、`node_modules`、路径含空格/中文。
  - 并发测试：3 个写入子运行各自独立，互不影响；清理后目录消失；失败时回退方案可用。
  - 安全测试：子运行不能通过 `..` 或绝对路径逃逸；不能读取主工作区之外的路径。
- **依赖**：M4-00、M4-01。
- **风险**：Windows 文件锁导致清理失败；延迟清理与下次启动清扫。Git 不可用时回退到复制式工作区，磁盘占用需要提示。

#### M4-08 实施记录

- 服务：新增 `apps/desktop/src/main/services/workspace-service.ts`，提供 `createIsolated`、`cleanup`、`list` 与启动清扫 `sweep`；目录为 `<appData>/Cairn/worktrees/<sessionId>/<runId>`，元数据放在同级的 `<runId>.workspace.json`，子运行自己的影子仓库放在 `<runId>.checkpoints.git`，都不会进入隔离工作区。
- 基线：以父工作区在委派时刻的检查点提交为基线。优先执行 `git worktree add --detach <path> <commit>`；worktree 失败时用 `read-tree` + `checkout-index` 从同一提交导出文件，因此项目本身不需要是 Git 仓库。导出式工作区同样不包含检查点排除项。
- 依赖：`node_modules`、`.venv` 以 Windows junction / 其他平台目录符号链接共享，不复制；链接失败只记录，不影响工作区创建。嵌套仓库、被 `.gitignore` 或检查点排除的文件不会进入工作区。
- 配额与清理：并发上限默认 8，磁盘上限默认 10 GiB；清理先 `git worktree remove --force` 再递归删除，失败时保留元数据，下次启动 `sweep` 重试；没有元数据的残留目录也会清扫。id 只接受安全字符，工作区与检查点路径必须与 `<worktrees>/<sessionId>/<runId>` 推导出的规范路径完全一致，篡改元数据不会导致清理任意目录。
- 宿主：`host.workspace.create` / `host.workspace.cleanup` 私有接口连接主进程；子运行的 `workspace.path`、工具注册、路径解析、检查点与改动记录都以隔离目录为根，主工作区不被写入。子运行使用独立的影子仓库（`refs/cairn/worktrees/<runId>`）并排除 `.git` 文件。
- 共享写入：宿主按会话维护写入队列，`shared` 方式同一时刻只允许一个写入类子运行；`isolated` 可以并行。`auto` 由目标 Agent 权限决定：只读 Agent 共享，写入类 Agent 隔离。创建隔离工作区失败（无检查点、配额、主进程不支持）时回退到共享写入并记录错误。
- 事件：没有新增 `workspace.*` 事件；`run.delegated` 已有 `workspace` 与 `workspacePath`，事件流仍以运行生命周期为主。
- 与计划的差异：`createIsolated` 额外接收项目影子仓库目录 `gitDir`（主进程按会话解析），服务本身无法仅从项目路径可靠推导项目 id；成功创建 / 清理的日志复用现有的 `onError` 与主进程错误上报，未引入新的日志服务。

### M4-09 改动集存储、合并与冲突

- **目的**：把隔离工作区中的改动变成可审阅、可接受、可拒绝、可回退的改动集。
- **设计依据**：[多 Agent 协作](../design/multi-agent.md) §7.3；ADR-0008、ADR-0031。
- **交付物**
  - 迁移 `0012-change-sets`：`change_sets`（id、sessionId、runId、parentRunId、baseCommit、workspacePath、status、createdAt、mergedAt）与 `change_set_files`（changeSetId、path、status、added、removed、patch/diff、binary/large 标记）。
  - 计算：子运行结束后，从基线提交到隔离工作区计算文件级 diff；二进制/超大文件只记录元数据，不进入模型上下文。
  - 合并：`changeset.get`、`changeset.apply`、`changeset.reject`、`changeset.resolveConflict`；按文件接受/拒绝；合并前在主工作区创建检查点；合并可回退。

### M4-13 多会话并行硬化

- **目的**：现有 3 宿主并行只是在调度层面存在；M4 要证明事件、审批、取消与改动记录在真实并发下不串会话。
- **设计依据**：架构 §4、§21；Runtime §10.1；ADR-0003。
- **交付物**
  - 并发测试：3 个会话同时运行；每个会话有独立的运行、审批、取消、检查点与改动记录；一个会话崩溃不影响其他会话。
  - 事件与审批按 `sessionId` 严格路由；活动中心聚合不改变原有会话内行为；空闲宿主回收与排队公平性。
  - 资源上限：宿主数、每会话运行数、每运行工具并发；超过上限时排队而不是失败。
  - 诊断：宿主崩溃时写入 `session.crashed`，不误伤其他会话；活动中心移除该会话的运行中项。
- **验收**
  - 集成测试：3 个会话 × 2 个子运行的并发；事件不串会话；审批只出现在所属会话与活动中心；取消只影响目标运行。
  - 性能测试：3 个会话同时流式输出时 UI 不卡顿；内存平稳；空闲 5 分钟后宿主回收。
- **依赖**：M4-01、M4-03、M4-06。
- **风险**：测试不稳定；用 FakeRuntime 与可控时钟做确定性并发测试，e2e 只做关键路径。
- **实施记录**
  - 运行名额（M4-13）：`RunSupervisor` 的 `maxRuns` 从“超限直接失败”改为“排队的软上限”。达到上限时根运行按 FIFO 进入队列（`maxQueuedRuns`，默认 32），释放或创建失败时补位；宿主关闭时拒绝排队中的创建与之后的新建。子运行（带 `parentRunId`）不排队：父运行在等待子运行期间无法释放自己的名额，排队会让父子互相等待；子运行数量由委派策略（并发、深度、每轮数量）约束，另加 `maxOverflowRuns`（默认 8）兜底。宿主侧默认每会话 8 个运行（`DEFAULT_MAX_RUNS`），覆盖“一个根运行 + 并行只读子运行”。
  - 并发集成测试：`host-integration.test.ts` 用内存通道 + 真实宿主 + FakeRuntime 同时运行 3 个会话，每个会话并行委派 2 个只读子运行；断言三个会话各 3 个运行、子运行 `parentRunId` 正确、运行 id 互不相交、各自 2 个 `run.delegated` / `run.child.completed`。另有两个隔离用例：取消一个会话只中止它自己的根运行与子运行，另外两个会话照常完成；杀掉一个宿主只写该会话的 `session.crashed`，其他会话继续完成。审批的跨会话聚合与按审批 id 路由由 M4-06 的 `activity-service.test.ts` 覆盖，会话内审批归属由 M4-03 的宿主测试覆盖，本任务不重复断言。
  - 性能验收：新增 `session-concurrency.perf.test.ts`（仅 `CAIRN_PERF` 下运行，加入 `test:perf`）：3 个会话同时逐字流式输出 3000 个增量，断言总耗时 < 20 s、事件间最大停顿 < 1 s、堆增长 < 256 MB，并在 `idleTimeoutMs` 之后确认 3 个宿主全部回收。阈值刻意宽松，用于发现调度退化与泄漏，不作为基准数据。
  - 边界：隔离工作区的并发上限（`workspace-service.maxConcurrent`）保持“超限快速失败”（`workspace.limit`）。工作区创建受磁盘配额与 Git worktree 开销约束，失败后宿主回退到共享工作区；把它改成排队会掩盖磁盘压力，也会让父运行长时间等待子运行的工作区。该行为在本任务保持不变并记录为边界。
  - 与计划的差异：`RunSupervisor` 的名额从创建起占用；根运行释放时归还，委派结束调用 `completeChild` 提前归还子运行名额，同时保留运行树可查询的运行，避免长会话连续委派耗尽名额。
  - 验证：`npx tsc -b`、`eslint .`、`prettier --check .`、`check-i18n`、`check-licenses`、桌面构建、E2E 37/37、smoke、`CAIRN_PERF=1` 性能测试通过；全量 Vitest 2970 通过（20 跳过），四项覆盖率 Statements 97.49%、Branches 95.03%、Functions 96.76%、Lines 98.48%，均 > 95%。

### 6.3 事件与顺序

- 所有事件继续由主进程分配 `seq`；子运行事件与父运行事件在同一个会话事件流中按发生顺序写入，不另建子运行日志。
- `run.delegated` 必须在子运行 `run.created` 之前写入；`run.child.completed` 必须在子运行 `turn.completed` 之后写入；父运行的 `awaiting_children` → `tooling` 状态转换以所有子运行结束为准。
- `changeset.created` 在 `run.child.completed` 之前写入，挂在父运行的 `runId` 上并带 `childRunId`；`changeset.applied` / `changeset.rejected` / `changeset.conflict` 同样挂父运行，避免子运行结束后事件失去归属。
- 试运行事件照常写入会话流，但 `session.list`、活动中心与用量统计默认排除 `kind = 'trial'`。
- 活动中心与检查器只读事件投影，不修改事件；界面不维护第二份运行状态。
