## 1. 范围与原则

本文档在 Runtime 委派原语（父子运行、`awaiting_children`、限额继承、权限收敛、取消传播）的基础上，设计多个 Agent 如何协作完成一个任务。

**原则**：

1. **单 Agent 是默认。** 多 Agent 会成倍增加模型调用和成本，只有任务确实可以拆分时才使用。
2. **以父运行为中心。** 子 Agent 只和派出它的父运行通信，彼此之间不直接对话（ADR-0020）。
3. **结构化交接。** 父运行发出结构化的任务书，子运行返回结构化的结果，而不是把整段对话互相转发。
4. **写入隔离。** 会修改文件的子 Agent 在隔离的工作区中工作，改动经审阅后才合并回主工作区。
5. **一切仍在掌控中。** 子 Agent 的每个操作都和单 Agent 一样经过权限判定、审批、检查点和事件记录，用户可以随时查看和停止任意一个子 Agent。
6. **有界。** 委派深度、并发数量、预算都有上限，不会出现无限递归或成本失控。

## 2. 什么时候值得用多 Agent

| 场景 | 收益 | 示例 |
|---|---|---|
| 大范围探索 | 子 Agent 读大量文件，只把结论带回，**节省父运行的上下文** | "找出所有使用旧版 API 的地方并归纳" |
| 可并行的独立子任务 | 缩短总耗时 | 同时为三个互不相关的模块补测试 |
| 独立审查 | 换一个视角、不受实现过程影响地检查结果 | 编码完成后由审查 Agent 检查 |
| 角色专长 | 使用专门的指令、Skills、权限或更合适的模型 | 只读的安全审查 Agent；用本地模型做大量简单检索 |

不值得的情况：任务很小、步骤之间强依赖、需要频繁和用户确认。此时多 Agent 只会增加成本和延迟。

系统提示词中会写明这些判断标准，引导主 Agent 只在合适的时候委派。

## 3. 协作模式

| 模式 | 描述 | 首次支持 |
|---|---|---|
| **委派** | 父运行把一个子任务交给一个子 Agent，等待结果后继续 | MA-1 |
| **并行分派** | 父运行同时派出多个子 Agent，全部返回后汇总 | MA-2（只读）、MA-3（写入） |
| **审查循环** | 实现 Agent 完成后交给审查 Agent，审查意见返回给实现方修改，最多 N 轮 | MA-4 |
| **团队模板** | 预定义成员、角色和流程（如：探索 → 实现 → 测试 → 审查），用户一键启用 | MA-4 |
| **工作流（DAG）** | 有依赖关系的多步骤流程，可定时或由事件触发 | MA-5（与自动化一起） |

**不做**：多个 Agent 在同一个"群聊"里自由对话、相互指挥。这种方式难以预测、难以调试、成本难以控制，而且对编程任务的收益不明显。

前三种模式都由同一个机制实现：父运行调用委派工具。区别只在于父 Agent 的指令和委派策略。团队模板是对这些设置的预先打包。

## 4. 通信模型

```
                 ┌──────────────┐
         用户 ◀──▶│  父运行（主控） │
                 └──┬────┬────┬─┘
             任务书 │    │    │ 任务书
                    ▼    ▼    ▼
               ┌─────┐┌─────┐┌─────┐
               │子 A ││子 B ││子 C │
               └──┬──┘└──┬──┘└──┬──┘
             结果 │      │      │ 结果
                  └──────┴──────┴──▶ 父运行汇总
```

- **父 → 子**：任务书（见第 6 节），通过委派工具的参数传递。
- **子 → 父**：结果（见第 6 节），作为委派工具的返回值。
- **子 → 用户**：只有审批请求会直接到达用户（标明来自哪个子 Agent）。子 Agent 不直接向用户提问；需要澄清时以 `needs_input` 状态返回父运行，由父运行决定是自己回答还是询问用户。
- **子 ↔ 子**：不直接通信。如果 B 需要 A 的结果，由父运行在 A 完成后把相关结论写进 B 的任务书。
- **用户 → 子**：用户可以在界面中停止某个子 Agent，或打开它的对话查看过程；第一版不支持用户直接向子 Agent 发消息，避免与父运行的指挥冲突。

## 5. 委派工具

委派以内置工具 `delegate` 的形式提供，工具类别为新增的 `delegate`。

```ts
interface DelegateInput {
  agent: string                       // 目标 Agent 定义 id，必须在父 Agent 的 allowedAgents 中
  task: string                        // 一句话目标
  brief: TaskBrief                    // 任务书，见第 6 节
  workspace?: 'shared' | 'isolated'   // 默认由目标 Agent 是否有写入权限决定
}
```

要点：

- 一个步骤中调用多个 `delegate` 即为并行分派，按调度规则（第 12 节）执行。
- `delegate` 经过完整的工具流水线：参数校验、`allowedAgents` 检查、权限判定（可配置为需要审批）、事件记录。
- 返回值是结构化结果（第 6 节），不包含子运行的完整对话。
- 父 Agent 只能看到 `allowedAgents` 中的 Agent，工具说明中列出这些 Agent 的名称和描述，帮助模型选择。

## 6. 任务书与结果

### 6.1 任务书

```ts
interface TaskBrief {
  goal: string                        // 要完成什么
  context?: string                    // 父运行掌握的相关背景（由父 Agent 撰写，长度有上限）
  files?: string[]                    // 建议优先查看的文件或目录
  constraints?: string[]              // 不能做什么、必须遵守什么
  deliverable: string                 // 期望交付什么
  outputSchema?: JsonSchema           // 如目标 Agent 定义了 outputSchema，自动带入
  budget?: Partial<RunLimits>         // 父运行希望的预算，不能超过可分配额度
}
```

### 6.2 结果

```ts
interface DelegateResult {
  status: 'completed' | 'failed' | 'aborted' | 'needs_input' | 'limit_reached'
  summary: string                     // 子 Agent 的总结（长度有上限）
  output?: unknown                    // 符合 outputSchema 的结构化输出
  changes?: {                         // 写入类子 Agent 的改动
    changeSetId: string
    files: Array<{ path: string; added: number; removed: number }>
    merge: 'pending_review' | 'merged' | 'rejected' | 'conflict'
  }
  question?: string                   // status 为 needs_input 时的问题
  usage: { tokens: number; cost?: number; durationMs: number; steps: number }
  childRunId: string                  // 供界面跳转查看完整过程
}
```

- 子 Agent 的最后一条回复会被要求按结果格式输出；系统负责解析和校验，校验失败时让子 Agent 修正一次，仍失败则把原文作为 `summary` 返回。
- 父运行只拿到结果，不拿到子运行的历史，这是多 Agent 节省上下文的关键。

## 7. 工作区与改动合并

### 7.1 三种工作区方式

| 方式 | 适用 | 规则 |
|---|---|---|
| 共享只读 | 只读的子 Agent（探索、审查） | 直接读取父运行的工作区；可以任意并行 |
| 共享写入 | 父运行在等待时，只有一个写入类子 Agent | 只允许串行；同一时刻只有一个写入者，由工作区锁保证 |
| 隔离写入 | 写入类子 Agent 需要并行，或用户希望审阅后再合并 | 子 Agent 在独立工作区中工作，结束后生成改动集，审阅后合并 |

### 7.2 隔离工作区的实现

- 以委派时刻的工作区状态为基础：先在检查点影子仓库（ADR-0008）中创建一个快照，这样即使项目不是 Git 仓库、或有未提交的改动，基础状态也是准确的。
- 从该快照检出一个独立工作区到应用数据目录（`%APPDATA%\NEXUS-OS\worktrees\<run id>\`），子 Agent 的 `workspacePath` 指向这里。
- 被检查点排除的目录（如 `node_modules`）不会复制；需要时通过链接共享只读的依赖目录，或让子 Agent 自行安装。具体方式在 M0 预研中与检查点一起验证。
- 子运行结束后，计算其工作区相对于基础快照的改动，生成**改动集**（ChangeSet）。

### 7.3 合并

- 改动集进入审阅：界面以 diff 展示，用户可以整体接受、按文件接受或拒绝（与单 Agent 的改动审阅一致）。
- 也可以在委派策略中配置为"由父 Agent 审阅"：父运行收到改动摘要后决定是否请求合并，但最终写入主工作区前仍按权限规则可能需要用户审批。
- **冲突**：如果主工作区中相同的位置在基础快照之后被修改过（例如另一个子 Agent 的改动已合并），标记为冲突。第一版处理方式：显示冲突的文件，用户选择保留哪一方，或把冲突交给父 Agent 处理。
- 合并前创建检查点，合并本身可以回退。
- 隔离工作区在改动集处理完毕后清理。

## 8. 上下文传递

- **子运行的上下文**：由子 Agent 自己的定义组装（基础提示词、子 Agent 指令、项目 `AGENTS.md`、Skills 索引、工具），加上任务书。不包含父运行的对话历史。
- **为什么不传历史**：父运行的历史可能很长，且大部分与子任务无关；传入会抵消多 Agent 节省上下文的收益，也会让子 Agent 被无关信息干扰。父 Agent 有责任在任务书中写清楚必要的背景。
- **父运行的上下文**：只增加委派工具的调用和结构化结果。
- **完整记录**：子运行的全部过程照常写入事件日志，用户可以在界面中查看；只是不进入父运行的模型上下文。

## 9. 权限与审批

### 9.1 有效权限

子运行的有效权限 = 子 Agent 定义的权限 ∩ 父运行当前的权限 ∩ 委派策略中的额外限制。

- 子 Agent 不能获得比父运行更多的权限。例如父运行是"只读"模式，即使子 Agent 本身允许写入，也只能只读。
- 系统强制规则对所有运行同样生效。
- 用户在审批中为父运行选择的"本会话始终允许"，对其子运行同样有效（因为属于同一会话），但仍受子 Agent 自身权限的限制。

### 9.2 审批的呈现

- 子 Agent 的审批请求出现在两个地方：父运行对话中对应的委派卡片内、活动中心。
- 每个审批都标明来自哪个 Agent、属于哪个任务。
- 并行的多个子 Agent 同时请求审批时，在委派卡片区域合并显示，支持逐个处理或"全部允许 / 全部拒绝"。

### 9.3 委派本身的审批

`delegate` 工具的默认权限：

- 委派给只读 Agent：允许。
- 委派给写入类 Agent：询问，审批卡片中显示目标 Agent、任务书摘要、工作区方式和预算。

用户可以按 Agent 调整这些默认值。

## 10. 预算与成本控制

### 10.1 委派策略

Agent 定义中 `delegation` 字段的结构：

```ts
interface DelegationPolicy {
  enabled: boolean
  allowedAgents: string[]             // 可以委派的 Agent 定义 id
  maxDepth: number                    // 默认 1：子 Agent 不能再委派
  maxChildrenPerTurn: number          // 默认 6
  maxParallel: number                 // 默认 3
  childBudgetShare: number            // 单个子运行最多可使用父运行剩余预算的比例，默认 0.5
  defaultWorkspace: 'auto' | 'shared' | 'isolated'
  mergeReview: 'user' | 'parent'      // 改动集由谁审阅，默认 user
}
```

### 10.2 预算规则

- 子运行的限额取以下三者中最小的：子 Agent 自身的限额、任务书中请求的预算、父运行剩余预算乘以 `childBudgetShare`。
- 子运行消耗的 token、费用、时间计入父运行本轮的消耗。父运行达到限额时，正在运行的子运行一起停止。
- 并行分派开始前，界面显示预计的最大消耗（各子运行预算之和）。

### 10.3 防止失控

| 风险 | 措施 |
|---|---|
| 无限递归 | `maxDepth` 默认 1；任何情况下全局深度上限为 3 |
| 循环委派（A → B → A） | 运行链上已出现的 Agent 不能再次被委派（深度大于 1 时生效） |
| 重复委派相同任务 | 与工具循环检测相同：相同 Agent、相同任务书的委派在同一轮中重复出现时提醒父 Agent，再次重复则拒绝 |
| 滥用委派做小事 | 系统提示词中给出判断标准；用量面板中按 Agent 显示消耗，方便用户发现问题 |
| 并发过多 | `maxParallel` 加上全局并发上限（总体架构第 4 节） |

## 11. 失败处理

| 情况 | 处理 |
|---|---|
| 子运行失败（模型错误、连续工具错误） | 返回 `status: failed` 和原因，父 Agent 决定重试、换 Agent 还是自己处理；系统不自动重试 |
| 子运行达到限额 | 返回 `limit_reached` 和已完成部分的摘要 |
| 用户停止某个子运行 | 返回 `aborted`，父运行继续，由父 Agent 决定后续 |
| 用户停止父运行 | 所有子运行一起停止，隔离工作区中的改动集保留，可以事后审阅 |
| 宿主进程崩溃 | 同一会话的父子运行都中断（它们运行在同一个会话宿主进程中），恢复时按 Runtime 设计第 13 节处理；未完成的子运行结果标记为"结果未知" |
| 合并冲突 | 见 7.3 |

并行分派时，一个子运行失败不影响其他子运行；父运行在所有子运行结束后一次性拿到全部结果。

## 12. 调度与状态

- 同一会话的父子运行都在该会话的 Agent 宿主进程中，由 `RunSupervisor` 统一调度（Runtime 设计第 4 节）。子运行的命令照常作为独立子进程执行，模型调用以网络 I/O 为主，因此在同一进程中运行多个子运行的开销可以接受。
- 父运行在某个步骤中发起委派后，进入 `awaiting_children`，直到该步骤中所有委派都返回。
- 一个步骤中的多个委派：
  - 全部是共享只读：并行，受 `maxParallel` 限制，超出的排队。
  - 有写入类、且使用隔离工作区：可以并行。
  - 有写入类、且使用共享工作区：串行执行。
- 运行树：`agent_runs.parent_run_id` 构成树状结构，事件中的 `runId` 与 `parentRunId` 用于界面重建运行树。

## 13. 界面

### 13.1 父运行对话中的委派卡片

```
┌─────────────────────────────────────────────────────────────┐
│ ⇉ 并行委派 3 个任务                        预计上限 120K token │
├─────────────────────────────────────────────────────────────┤
│ ◇ 代码探索  查找所有使用旧版 API 的调用    ✓ 完成 · 18K · 1 分钟 │
│ ◇ 代码探索  梳理 auth 模块的依赖关系      ◌ 第 6 步 · 9K        │
│ ◆ 测试补全  为 utils 补单元测试  [隔离]   ⚠ 等待审批：执行命令    │
│                                    [查看] [允许] [拒绝]       │
└─────────────────────────────────────────────────────────────┘
```

- 每个子任务一行：Agent、任务、状态、用量。
- 点击一行展开，查看该子运行的完整过程（与普通对话相同的展示方式，只读）。
- 写入类子运行完成后，行内显示"查看改动（+42 −5）"，进入改动集审阅。

### 13.2 运行树

- 检查器的"时间线"标签中，运行以树状结构显示：父运行 → 子运行 → 各自的轮次和步骤。
- 用量标签中按 Agent 分组显示消耗。

### 13.3 改动集审阅

- 与单 Agent 的 diff 视图一致，顶部显示来源（哪个子 Agent、哪个任务）、基础快照时间、冲突数量。
- 操作：全部接受、按文件接受、拒绝、交给父 Agent 处理冲突。

### 13.4 Agent 编辑器中的委派设置

- 管理界面"高级"分区中的委派设置在 MA-1 阶段启用，对应 `DelegationPolicy` 的各字段。
- `allowedAgents` 以多选列表呈现，只能选择已发布的 Agent。

### 13.5 消息中的 Agent 标识

多 Agent 会话中，每条消息都显示 Agent 图标和名称（管理界面设计 7.3 节）。

## 14. 内置专业 Agent

随多 Agent 功能逐步加入的内置 Agent：

| Agent | 权限 | 用途 | 阶段 |
|---|---|---|---|
| 编程助手 | 询问 | 主控，可委派给下面的 Agent | 已有 |
| 代码探索 | 只读 | 大范围阅读、查找、归纳 | 已有，MA-1 起可被委派 |
| 代码审查 | 只读 | 审查改动，按严重程度输出问题清单（定义 `outputSchema`） | MA-2 |
| 测试补全 | 写入（仅测试文件）+ 执行（测试命令） | 编写并运行测试 | MA-3 |

不单独设立"规划 Agent"：编程助手本身负责规划和汇总，避免多一层传话。

## 15. 团队模板（后续）

在 MA-4 阶段引入，用于把常用的协作方式打包：

```ts
interface AgentTeam {
  id: string
  version: number
  name: LocalizedText
  description: LocalizedText
  coordinator: string                 // 主控 Agent
  members: string[]                   // 可被委派的 Agent
  pattern: 'delegate' | 'review-loop' | 'pipeline'
  pipeline?: Array<{ agent: string; stage: string; dependsOn?: string[] }>
  reviewLoop?: { maker: string; checker: string; maxRounds: number }
  delegation: Partial<DelegationPolicy>
}
```

- 团队与 Agent 一样有版本、草稿、发布、试运行。
- 会话中可以选择"团队"代替单个 Agent，实际运行时以主控 Agent 为根运行。
- `pipeline` 是有依赖关系的固定流程，为以后的工作流引擎打基础。

## 16. 对现有设计的影响

| 位置 | 改动 |
