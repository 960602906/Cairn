# ADR-0022 输入优化：由用户触发、确认后发送

- 状态：已废弃（2026-11-05）
- 日期：2026-11-02

> **已废弃**：2026-11-05 决定不做输入优化。用户输入什么就发送什么，不提供改写草稿的按钮。以下内容只作为记录保留。

## 背景

用户输入的任务描述往往比较简短，例如“登录有问题，修一下”，缺少目标、涉及的范围和验收标准。模型据此工作，容易猜错方向或多走弯路。

现有设计都是在用户输入之外补充背景：系统提示词分层（基础提示词、`AGENTS.md`、用户自定义说明）、会话要点、计划模式。没有一项处理用户输入本身。

## 决定

- 输入框旁提供“优化”按钮（另设快捷键）。用户点击后，用模型把当前草稿改写成更完整的任务描述，结果**放回输入框**，用户确认或修改后再自己发送。
- **不在发送时自动改写**。发出去的、写进历史的，始终是用户最终确认的文本。
- 改写只补充用户已经表达或可以从项目中查到的信息：目标、涉及的文件或模块、约束、验收标准。不确定的地方写成待确认的问题，而不是替用户做决定。保持用户的语言。
- 改写使用辅助模型（`ModelSelection.auxiliary`），未配置时用主模型。
- 改写时可用的上下文：项目说明（`AGENTS.md`）、会话要点、最近几轮对话的摘要、工作区的文件列表。不调用工具，不修改文件。
- 改写不是一轮对话：不产生 `turn.*` 事件，不进入对话历史。它消耗的用量照常记录，标明用途为输入优化。
- 用户可以撤销改写，恢复原来的草稿；改写进行中可以取消。

## 备选方案

- **发送时自动改写**：用户看不到改了什么，模型可能曲解原意；每次发送都多一次模型调用，增加延迟和费用。
- **自动改写并在设置中可选**：多一套配置与两种行为要维护，收益不明显；先做按钮，有需要再加。
- **只靠系统提示词要求模型先澄清需求**：保留，作为基础提示词的一部分（需求不清楚时先提问），但它不能帮助用户把需求写清楚。

## 后果

- 新增一个请求（暂定 `prompt.enhance`，参数为会话 id 与草稿，返回改写后的文本），由主进程交给会话的宿主执行模型调用；凭据仍只在宿主中使用（ADR-0010）。具体接口在实现时定义。
- 需要真实模型，计划在 M2 交付（设置页、模型切换之后）；M3 引入辅助模型后改用辅助模型。
- 输入框需要“优化中”“撤销优化”两种状态；草稿与优化结果都只在界面中，不落库。
