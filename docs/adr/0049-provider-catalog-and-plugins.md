# ADR-0049 供应商目录与声明式供应商插件

- 状态：已接受（实施）
- 日期：2026-11-27
- 相关决策：ADR-0010、ADR-0011、ADR-0017、ADR-0021
- 相关文档：[架构设计](../architecture.md) §12；[供应商插件](../dev/provider-plugins.md)

## 背景

添加供应商时，界面先按接口格式（Anthropic / OpenAI / Gemini）分组，每组只有一两个官方模板。
通义千问、Kimi、智谱 GLM、SiliconFlow、OpenRouter 以及本机的 Ollama 都只能走“自定义”：用户
要先知道服务用哪种接口格式，再自己填地址，还要猜兼容参数（推理参数格式、输出上限字段等）。运行时
虽然已经支持 `qwen` / `openrouter` / `zai` 这些推理参数格式，但没有模板把它们配好。

[Magpie](https://github.com/yetone/magpie) 的“添加供应商”给了另一种思路：列出已知的厂商与中转，
选中后只需粘贴 Key；同一服务的国际站与中国大陆站作为接入点切换；本机服务不要求 Key；更多服务由插件
提供。Magpie 的插件是在 Bun 上运行的 OpenCode 插件代码，能改写请求。Cairn 没有插件运行时，
也没有插件市场（架构 §1 把插件市场列为非目标），现有的扩展点（Skills、MCP、自定义 Agent）都是
“用户目录里的文件 + 设置页安装 / 卸载”。

## 决定

- **目录代替按格式分组。** `@cairn/core` 的 `PROVIDER_TEMPLATES` 扩展为服务目录，每项带类别
  （`vendor` 模型厂商 / `relay` 聚合平台与中转 / `local` 本机运行）、接口格式、默认地址、可选的接入点
  （`global` / `cn`）、申请 Key 的页面、兼容参数、预置模型或建议模型。添加对话框按类别分组、可搜索，
  接口格式只作为目录项的属性出现，用户不必先选。
- **只填 Key。** 选中目录项后进入编辑弹窗，焦点在 Key 输入框；中文界面默认选中国大陆接入点。
  没有预置模型的服务在填入 Key 后自动拉取模型列表（本机服务打开即拉取），并启用 `suggestedModels`
  中服务确实列出的模型；本机服务没有建议时启用拉取到的前几个模型。建议的模型 id 只是偏好，服务没有
  列出就忽略，所以目录不需要跟着各家的模型发布频繁更新。
- **只收录可靠的地址。** 内置目录只放官方接口与公认的聚合平台（OpenRouter、SiliconFlow、
  Vercel AI Gateway），不收录非官方中转；其余用“自定义”或插件接入。
- **自定义保留。** 三种接口格式各有一个“自定义”入口，得到空白草稿，与之前相同。
- **插件是只有数据的 JSON 文件。** 一个插件声明一个或多个服务，格式由 `@cairn/protocol` 的
  `ProviderPluginManifest` 定义（`schemaVersion: 1`），展开后与内置目录项是同一结构
  （`ProviderTemplateSpec`），模板 id 为 `<插件 id>.<条目 id>`，不会与内置模板重名。插件不含代码，
  不改写请求；协议差异仍只由 `runtime-pi` 按 `kind` 与 `compat` 处理（ADR-0021）。
- **沿用 Skills 的安装方式。** 插件放在应用数据目录的 `provider-plugins/` 下，由主进程扫描
  （`provider-plugin-service`）。设置页“从文件安装”先校验并预览插件中的服务与地址，确认后以
  `<插件 id>.json` 写入；同 id 的旧插件被替换。无法加载的文件列出原因，不挡住其余插件。
  IPC 为 `providerPlugin.list / pick / install / remove`。
- **目录只在添加时使用。** 与原有模板一样，创建时把值复制进 `ProviderConfig`，`template` 只记录来源。
  卸载插件或目录变化都不影响已保存的供应商；找不到模板时按普通的第三方中转显示。原有四个模板的 id、
  地址与模型不变，已保存的配置与凭据不需要迁移。
- **编辑器的三处修正一并做：**
  - 关闭有未保存改动（包括新填的 Key）的编辑弹窗前先确认；
  - 保存时先写 Key：写入失败就不改设置；设置写入失败时撤回刚写入的新 Key，替换掉的旧 Key 无法恢复时
    如实说明；
  - “测试连接”默认只测一个模型（默认模型或第一个启用的模型），测试全部模型要再确认一次。

## 备选方案

- **继续按格式分组，只多加模板。** 用户仍要先知道服务用哪种格式，问题没有解决。
- **运行代码的插件（类似 Magpie / OpenCode）。** 能接入需要自定义鉴权或请求改写的服务，但需要插件
  运行时、沙箱与权限模型，插件还能接触 Key 与请求内容。目前的需求只是“多几个预填好的服务”，声明式
  数据足够；以后确有需要再单独决策。
- **把供应商做成一种 Skill。** Skill 是交给模型的说明，生命周期、启用状态与作用域（项目内技能）都
  不适合供应商配置；共用目录只会让两者互相牵制。
- **从远程目录拉取服务列表。** 需要可信的发布渠道与离线策略，不符合“默认不联网”的做法；可以以后作为
  插件的一种来源。

## 后果

- 新增服务通常只需在目录里加一项，或由用户安装插件，不需要改界面。
- 插件只能声明 Cairn 已支持的三种接口格式与已有的兼容参数；格式不同的服务仍需在 `runtime-pi`
  中适配。
- 插件声明的地址会收到用户为它填写的 Key。安装前的预览列出每个服务的地址，并提示只安装信任的插件。
- 建议模型列表可能过时；过时只意味着自动启用的模型少一些，用户仍可在列表中打开其他模型。
