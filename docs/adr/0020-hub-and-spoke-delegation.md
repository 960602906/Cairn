# ADR-0020 多 Agent 采用以父运行为中心的委派模式

- 状态：已接受
- 日期：2026-11-02
- 详细设计：[多 Agent 协作设计](../design/multi-agent.md)

## 背景

多 Agent 协作有多种做法：主控委派、多个 Agent 在同一对话中自由讨论、预定义流程等。自由讨论的方式难以预测、难以调试，成本也难以控制。另外，多个能写文件的 Agent 同时修改同一个工作区，容易互相覆盖。

## 决定

- 采用**以父运行为中心**的委派（hub-and-spoke）：父运行通过 `delegate` 工具向子 Agent 发出结构化任务书，子 Agent 返回结构化结果。子 Agent 之间不直接通信。
- 子 Agent 不继承父运行的对话历史，只接收任务书和系统自动附加的会话要点（用户的目标与明确约束）；父运行只接收结果，不接收子运行的历史。
- 子运行的有效权限为子 Agent 权限、父运行权限与委派策略的交集。
- 预算从父运行中分配，消耗计入父运行；默认委派深度为 1。
- 只读子 Agent 共享父运行的工作区；写入类子 Agent 串行使用共享工作区，或在基于检查点快照创建的隔离工作区中并行工作，改动集经审阅后合并。
- 审查循环、团队模板、工作流都建立在这一机制之上。

## 备选方案

- **自由对话（群聊式）**：灵活，但不可预测、成本高、调试困难。
- **子 Agent 共享父运行的完整历史**：实现简单，但抵消了节省上下文的收益，也会引入无关干扰。
- **所有写入类子 Agent 共享工作区并行**：实现简单，但会互相覆盖改动。

## 后果

- 父 Agent 需要写清楚任务书，系统提示词中需要给出委派的指导。
- 需要实现隔离工作区和改动集合并，复用检查点基础设施。
- 每个协作过程都可以通过运行树和事件日志完整追溯。
