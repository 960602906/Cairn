# ADR-0045 自动修复的推送边界：受控 Git 工具与分支守卫

- 状态：已接受（实施）
- 日期：2026-11-18
- 相关决策：ADR-0007、ADR-0010、ADR-0018、ADR-0026、ADR-0031
- 相关文档：[自动修复设计草案](../plan/auto-fix.md)；[Agent Runtime 详细设计](../design/agent-runtime.md)

## 背景

`docs/plan/auto-fix.md` 要求自动修复能“修、验证、提交并推送”，但在落地前先写一份 ADR：
自动推送会没有用户在场地改动远端 PR 分支，且需要 GitHub 令牌（写入权限）。设计草案没有说明
推送由谁执行、令牌放在哪里、模型能做什么不能做什么。

约束：

- 修复会话是无人值守运行（ADR-0018），没有人能审批，审批卡片一旦弹出就不会有人回答；
- 令牌存在主进程的凭据存储里（ADR-0010），不应跨进程序列化，更不应进入日志、事件或命令行参数；
- 修复跑在隔离 worktree（ADR-0031），模型可能运行任意命令，不能信任它“只会推对分支”；
- 不自动合并、不强制推送（设计草案 §1）。

## 决定

- **只注册两个专用工具。** `git_commit`（参数只有提交说明）与 `git_push`（无参数）。工具只在
  主进程通过 `host.init.autoFix` 明确声明“这是自动修复会话”时才注册；宿主没有存储，不能自己
  判断会话种类。其他会话里模型看不到这两个工具；权限守卫再拒绝一次，即使将来被错误注册也不会执行。
- **执行放在主进程。** 宿主只做代理：`host.git.commit` / `host.git.push` 回到主进程，由自动修复
  服务重新校验会话（`getBySession`）、监视与 worktree 后再执行。令牌只存在于主进程，随一次推送
  子进程的环境传入（`GIT_CONFIG_*` 的 `http.https://github.com/.extraheader`），不进入 argv、事件、
  错误参数或日志；错误文本中的远端凭据会被遮掉。
- **提交使用受控身份。** `git add -A` + `git -c user.name=Cairn -c user.email=cairn@users.noreply.github.com
  commit`：不改用户 Git 配置、不接受 amend，提交对象只可能落在监视 worktree 的分支历史上。
- **分支守卫以最新的 PR 快照为准。** 推送前先 `fetch`，再读取 PR：PR 必须仍为打开状态；head 必须
  与监视的仓库相同（fork 的同名分支——比如也叫 `main`——不能推到基准仓库）；PR 当前的 head 提交
  必须已在本地；`merge-base --is-ancestor <PR head> HEAD` 必须成立（不得改写已推送的历史、不得推
  别的历史）；HEAD 与 head 相同则报“没有需要推送的提交”。推送目标固定为
  `https://github.com/<repo>.git HEAD:refs/heads/<PR headRef>`，加 `--no-verify`，没有 `--force`
  与任何其他 refspec。任一条件不满足即失败，交由模型改正，而不是放宽守卫。
- **无人值守时审批立即拒绝。** 审批门在 `unattended` 运行里直接返回 `deny`，不等待一个不会到来的
  决定。自动修复会话的权限预设（来源 `preset`）放行 `write` 与 `execute`，让模型能改代码、跑检查；
  命令类守卫仍先于规则生效，因此 `start_command` 里的 `git push` 仍会被要求审批并随即拒绝——
  推送只能走 `git_push`。
- **推送后回检。** 推送成功后任务记为 `pushed`。下一轮轮询若检查全部结束且没有失败（或没有检查
  且分支不再冲突），任务记为 `passed` 并通知用户；仍有失败则按新的去重签名进入下一次尝试，达到
  次数上限时关闭监视、记录 `gave_up` 并通知。

## 备选方案

- **让模型用 `start_command` 执行 `git push`**：令牌必须进入 shell 环境或远端 URL，模型还可以加
  `--force`、推别的分支；守卫无从实施。否决。
- **把令牌交给宿主，由宿主推送**：令牌跨进程序列化，宿主与被模型间接影响的代码在同一个进程里，
  暴露面更大；主进程已经有 worktree、监视与 GitHub 客户端。否决。
- **允许强制推送以“修好冲突”**：会覆盖他人已推送的提交，与设计草案的禁令冲突。否决。
- **只靠系统提示词约束模型**：无法审计也无法保证，提示词不是安全边界。否决。
- **推送前要求用户确认**：修复会话是无人值守的，确认等于把任务永久挂起；改为事后通知结果。否决。

## 取舍与后果

- 新增两个工具名与一对宿主→主进程请求；协议与宿主都按“只有自动修复会话才注册”处理，测试覆盖
  会话外不可见、被拒绝两处。
- 推送必然先 `fetch` 并读取 PR：GitHub 不可用时推送失败（失败关闭），不会凭缓存推送。
- 守卫只认 GitHub 托管的仓库（令牌按 `https://github.com` 注入），且只支持同一仓库内的 PR 分支
  （fork PR 的修复与推送在后续阶段设计）。其他主机需要另行设计。
- 模型如果提交了不该提交的文件，`add -A` 会一并推送；隔离 worktree 每次从 PR head 重置，影响
  范围限于该 PR 分支。用户仍可在 PR 上审查并回退。
- 通知只在 `passed` / `gave_up` 时发出，且尊重“活动通知”设置；通知失败不影响任务状态。
- 目前不自动合并、不在 PR 上回写评论；后续如需要，应在同一守卫之上增加，而不是放宽本 ADR。
