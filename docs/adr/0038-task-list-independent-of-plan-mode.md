# ADR-0038 待办列表独立于计划模式

- 状态：提议
- 日期：2026-11-13
- 相关决策：ADR-0005、ADR-0028、ADR-0030

## 背景

ADR-0028 定义的计划模式是**一轮运行方式**：这一轮只读地调查并提出结构化方案，待用户批准后才执行。待办列表则是**可持久化的数据与视图**：一组有稳定 id、顺序和状态的任务项，执行期间可以增删、改名、调整顺序及更新进度。是否需要审批方案，与是否需要跟踪工作，不是同一个判断。

目前没有独立的待办实体。`PlanDocument.steps` 至多 20 项；`propose_plan` 是创建它们的唯一入口，批准后才成为有 `pending`、`in_progress`、`done`、`skipped` 状态的列表。`update_plan_step` 和 `revise_plan_steps` 依赖活动中的已批准计划，否则返回 `plan.no_active_plan`。`PlanProgress` 则直接读取 `PlanView.steps`。因此，正常执行中途无法按需新建 checklist；较大的任务既受 20 步上限约束，也被迫使用“先提案、再批准”的计划语义。多 Agent 委派同样需要跟踪任务及其归属，不宜为了显示进度而假装它们全是计划步骤。

## 决定

- **保留计划模式的运行语义。** 只读限制、`propose_plan`、用户批准／重规划／放弃的流程及方案正文（目标、文件、风险、验证方式）仍属于 Plan；拥有待办列表不改变权限，不触发计划审批，列表完成也不等于计划获批。
- **抽出独立的 `TaskList` / `TaskItem` 领域实体。** 一份列表有稳定 `listId`、会话归属、标题或目标、来源（如 `ad_hoc`、`plan`、`delegation`）及有序任务项；每项有稳定 `itemId`、标题、状态和可选说明。状态沿用 `pending`、`in_progress`、`done`、`skipped`。列表可从普通执行轮次创建和修订，不依赖已批准计划；不要求每个会话都有列表。列表及每项容量限制单独制定，不直接继承 `PLAN_STEP_MAX`，必要时允许拆成多份列表或层级任务，而不是无限放大单份方案。
- **事件日志仍是事实来源。** 定义独立的列表创建、项目增删／改名／排序、状态变更及列表关闭事件，在会话投影中重建列表。事件携带 `listId`、`itemId`，并保留来源关联（如 `planId`、委派的 `runId`）；重复创建、未知 id、非法状态迁移与旧事件重放均需有明确规则。不要把列表作为另一份不可追溯的可变状态存储。
- **计划步骤成为列表的一个来源，而非列表本身。** 提案阶段 `PlanDocument.steps` 仍是供审批的草案；批准时以批准后的标题一次性创建或关联执行列表，保留计划与列表的双向关联及稳定的步骤映射。此后进度和执行期修订以列表事件为准；方案正文保留审批时的快照，不因随手增删待办而悄悄改写已批准的内容。需要改变方案本身时仍走重规划／再次审批。未批准或被放弃的提案不自动产生执行列表；较早已批准计划的列表也不应被无关提案覆盖。
- **工具收敛到列表操作。** 提供创建列表、修订任务项和更新状态的通用能力；正常轮次可在没有活动计划时使用。计划执行提示词使用同一能力，传入关联列表与项目 id。旧 `update_plan_step`、`revise_plan_steps` 的对外兼容和退出策略在实施时明确，避免长期维护两套语义相同的写入口；计划轮次只读限制继续生效，不因列表工具归类为 read 而允许绕过提案审批或修改现有执行列表。
- **进度 UI 读通用列表投影。** 将 `PlanProgress` 的任务行、计数与折叠行为泛化为 TaskList 视图；计划摘要卡、方案详情和审批按钮仍独立。计划来源的列表可跳转至方案，临时列表无需伪造计划。多 Agent 委派可关联任务项，但委派运行状态、取消和权限仍以运行事件及委派协议为准，不以勾选任务项代替。

## 备选方案

- **轻量方案：仍把计划步骤当待办，只放松入口和上限。** 允许正常轮次直接建 `PlanDocument`，放宽 20 步限制，再复用 `plan.*` 事件与卡片。改动较小，但“没有审批的计划”“委派即计划”语义混乱；方案快照与执行中 checklist 的修订难分，未来仍须迁移领域模型。不采用。
- **重型方案：完全独立的 Todo，计划和 Todo 各自维护步骤与状态。** 两者可以各自演进，但批准后需双写并同步完成度、改名和删除；事件重放时容易出现两套真相。不采用。这里的独立是指实体、入口和生命周期独立，不是复制一份执行进度：计划仅保存审批快照，执行状态统一归 TaskList。

## 后果

- 协议须新增列表 schema、来源关联与版本化事件；计划相关历史事件及旧 `PlanView` 仍要可重放，不能直接改写已落库的 `plan.*` payload。迁移可在投影层把历史已批准计划的步骤映射为兼容列表，再让新事件写入通用列表；确定性的 id、旧步骤下标事件与修订后的 id 对齐须有测试覆盖。
- Core 的会话投影、宿主的活动列表选择和运行时工具显隐需从 `activeExecutionPlan` 解耦。一次会话可能同时存在多份列表；工具必须显式指向列表，不得把“最近的计划”默认为所有任务的容器。提案、批准和执行中的时序尤其要验证。
- Desktop 的悬浮进度卡、侧栏和国际化文案需支持有计划和无计划的列表；计划审批交互保持原样。界面“可勾选”对应明确的状态变更操作，而非只改本地显示，并须处理并行运行的状态更新。
- 需要分别测试普通轮次创建／修订列表、计划批准后的关联和状态更新、重规划与放弃、旧事件重放、跨轮次恢复，以及委派关联；本 ADR 不规定具体工具名称、列表硬上限或交互布局，实施设计与验收时再定。
