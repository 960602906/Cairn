# ADR-0044 用户提问：`ask_user` 工具与选项卡片

- 状态：已接受（实施）
- 日期：2026-11-16
- 相关决策：ADR-0005、ADR-0017、ADR-0018、ADR-0024、ADR-0038
- 相关文档：[架构设计](../architecture.md) §7、§9、§10、§15；[视觉规范](../design/visual-style.md) §6

## 背景

模型需要澄清需求时，基础提示词只让它“先问一个简短的问题”。实际效果是模型在回复里写一段
问题，然后这一轮结束；用户必须切到输入框重新打字。界面没有把问题变成可选择的选项，模型也拿
不到结构化的答案。

界面上已有的用户决策卡片都各有用途：审批卡片处理工具权限，计划卡片处理 `propose_plan`，
委派卡片处理子运行的 `needs_input`。没有一种卡片用于“模型向用户提问并等待回答”。委派的
`needs_input` 只回传给父运行，不是给用户的提问界面。

## 决定

- **新增内置工具 `ask_user`。** 类别 `read`、不需要审批、`parallel: false`（等待回答期间
  不能同时执行其他工具，问题按模型给出的顺序出现）。一次调用带 1～4 个问题，每个问题 2～6
  个选项；每个选项可以有说明，最多一个标为 `recommended`。用户始终可以填写自定义回答。
- **阻塞式工具，同一轮继续。** 宿主经 `host.question.request` 请主进程转给界面，用户回答
  后作为工具结果回给模型，模型继续这一轮。不采用“结束这一轮再让用户重新输入”的做法，也
  不要求模型把问题拆成多次调用。
- **复用审批的传输结构。** 主进程新增 `QuestionService`，与审批服务一样只在内存中保存未决
  请求：界面经 `question.pending` 读取、`question.resolve` 回答，变化时推送 `question.changed`；
  宿主取消时发 `host.question.cancelled`；宿主退出、崩溃或应用重启时由监督器取消。未决提问
  不写事件日志：`tool.requested` / `tool.completed` 已经记录了问题与回答，足以重放和审查。
- **提问卡片浮在输入框上方，一次只问一个问题。** 卡片不占消息流的位置，浮在输入框之上；
  一次多个问题时逐题显示，回答后“下一个”，可以“上一个”改答案；最后一个问题才出现“提交”。
  只有一个单选题时，点选项立即提交。推荐项带“推荐”标记并高亮，但不预先选中。会话状态增加
  `waiting_input`（侧栏仍由主进程汇总，不区分提问）。
- **可以取消整张提问。** 卡片左下角“取消”放弃这次提问：主进程按 `cancelled: true` 结束请求，
  工具结果告诉模型用户没有回答。模型不应立刻重复提问，而是按最合理的判断继续并说明做出的
  假设，或用普通文字说明还需要什么。取消不是结束这一轮，运行照常继续。
- **子运行不直接提问。** 委派子运行的工具流水线不提供 `askUser`，`ask_user` 在那里报不可用；
  子运行需要澄清时仍以 `needs_input` 返回父运行，由父运行决定自己回答还是用 `ask_user` 问用户。
- **只在工具可见时加提示词。** 系统提示词在 `ask_user` 对该 Agent 可见时加入“需要决定或补充
  信息时调用 `ask_user`，标出推荐项”的说明，避免没有这个工具的 Agent 被误导。
- **无人值守运行不注册提问工具。** 没有用户在场时等待回答没有意义（ADR-0018）；工具不可见，
  模型按现有规则自行决定或返回结果。

## 备选方案

- **继续用纯文本提问（现状）**：模型拿不到结构化答案，这一轮提前结束，用户还要再输入一次，
  否决。
- **仿照计划卡片：`stopLoop` 后结束这一轮，用户点选项再发一条消息**：交互轮次多一次，回答也
  不是工具结果，模型更难把它当作本轮输入的一部分，否决。
- **多个问题拆成多次工具调用**：每次都要等一轮回答，串行往返明显变慢；一次调用带多个问题
  可以在一个卡片里收齐，采用后者。
- **把推荐项做成默认提交**：用户可能没看清就提交，保留“高亮 + 标记”而不自动选中。

## 取舍与后果

- 协议新增 `host.question.request` / `host.question.cancelled`、`question.pending` /
  `question.resolve` / `question.changed` 与对应的类型；主进程、宿主、渲染进程各多一条链路，
  与审批链路的维护方式一致。
- 未决提问只在内存中，应用重启后不会恢复；正在运行的宿主会把这一轮按中断处理。
- 活动中心目前只把提问中的会话显示为“运行中”，还没有“待回答”的入口；后续可以像审批一样
  聚合到活动中心。
- 提问卡片一次最多 4 个问题；需要更长的表单或条件分支时，模型可以再次调用 `ask_user`。
- 取消依赖模型遵守提示：工具结果里明确写了“不要立刻重问”，但模型仍可能换个说法再问；
  这时用户可以直接停止这一轮。
