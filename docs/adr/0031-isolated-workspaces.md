# ADR-0031 隔离工作区与改动集合并

- 状态：提议（M4-00 起草；M4-08 / M4-09 定稿）
- 日期：2026-11-08
- 详细设计：[多 Agent 协作](../design/multi-agent.md) §12、§13；[架构](../architecture.md) §11、§26
- 相关决策：ADR-0008、ADR-0020

## 背景

写入类子 Agent 如果直接在父工作区修改文件，多个子运行会互相覆盖，也无法在合并前审阅。ADR-0008 已经为每个项目维护影子 Git 仓库与检查点，但还没有决定如何从检查点创建隔离工作区、如何收集改动、如何合并与回退。

候选方案：

1. 复制整个项目目录；
2. 共享父工作区，写入类子运行串行；
3. 从影子仓库的检查点提交创建 `git worktree`；
4. 从影子提交导出文件到一个独立目录。

方案 1 在大型项目上磁盘与时间成本过高；方案 2 无法并行，也不满足“多任务并行互不干扰”；方案 4 可行但会丢失 Git 的索引与状态能力，只适合作为回退。

## 决定

- **以检查点提交为基线。** 委派写入类子运行时，先为父工作区创建检查点，再以该提交为基线创建隔离工作区。
- **使用 `git worktree add --detach`。** worktree 的 Git 目录指向项目影子仓库，工作区放在应用数据目录下的 `worktrees/<sessionId>/<childRunId>/`；基线提交是 detached HEAD。
- **沿用影子仓库的排除规则。** `node_modules`、超大文件、嵌套仓库与 `.gitignore` 排除项不进入隔离工作区；需要依赖时由服务创建 `node_modules` 的 junction / symlink（Windows）或目录符号链接（其他平台），不复制依赖。
- **改动集以基线提交为起点。** 子运行结束后，用 worktree 的 `git status` / `diff` 生成文件级改动集，保存基线提交、文件列表、diff 与状态；M4 只做文件级接受 / 拒绝，不做块级自动冲突合并。
- **合并前创建检查点。** 接受改动集前先为父工作区创建检查点；合并后可以把检查点作为回退目标。
- **冲突处理。** 主工作区在基线与合并之间发生变化时，按文件报告冲突；用户选择保留主工作区、采用子运行版本或手动处理。交给父 Agent 自动解决留到 MA-4。
- **回退与清理。** worktree 使用 `git worktree remove --force` 清理并 `prune`；应用启动时清扫上次留下的 worktree；删除失败时记录诊断但不阻塞启动。
- **回退方案。** 文件系统不支持 worktree、路径过长、权限异常时，从影子提交把文件导出到独立目录；导出式工作区不能使用 Git 索引，改动集由文件哈希与内容比较生成。
- **嵌套仓库不保护。** 嵌套仓库不在检查点内，也不会出现在隔离工作区；界面必须明确说明。

## 备选方案

- **复制项目目录**：简单但代价高，不采用。
- **共享工作区串行写入**：保留为“共享写入”模式，但不是并行写入的默认方案。
- **直接使用用户的 Git 仓库创建分支**：会污染用户的提交历史与分支，不采用。

## 后果

- 每个写入类子运行需要一个独立的 worktree 目录；同一项目的多个 worktree 共享影子仓库对象与索引锁，必须沿用锁重试与清理策略。
- 隔离工作区不会自动获得依赖；界面与日志需要说明 junction / symlink 的创建结果。
- 改动集必须记录基线提交，否则无法判断主工作区后来发生的改动是否构成冲突。
- 磁盘占用增加；M4 需要提供 worktree 清理与改动集保留策略。
