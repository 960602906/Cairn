# ADR-0028 计划模式：结构化计划、只读轮次与两个工具

- 状态：已接受
- 日期：2026-11-07

## 背景

Runtime §25.1 要求一轮只读地提出计划，用户批准后再执行。协议里已经有 `plan.proposed`、`plan.approved`、`plan.rejected`、`plan.step.updated`，但 `content` 只是一段字符串，运行时也没有写入过。计划要能改步骤、显示进度，字符串不够用。

权限引擎里，强制拦截比规则更严，allow 规则不能把它放开。计划模式需要的就是这种“这一轮一律不能改”的限制，而不是把用户的权限模式改成只读。

## 决定

- 计划是结构化的：`goal`、`files`、`steps[{ id, title }]`、`risks`、`verification`，另留一份 `markdown` 给界面显示。`plan.proposed` 的 `content` 换成这个结构。这个事件没有历史数据，事件版本不升。
- 步骤 id 由模型给出，不跟显示顺序绑死。`plan.step.updated` 仍用已有的 `stepIndex`。工具 `update_plan_step` 接收 `stepId`，宿主把它换成下标。偏离计划不拒绝，说明写在可选的 `note` 上。
- 计划这一轮多一条强制拦截：类别是 write、execute、network 的调用直接拒绝，原因说明计划模式下只能阅读。用户的“自动”模式和审批生成的 allow 规则都不能放开它。这一轮结束拦截就撤掉，不改全局权限。
- 两个工具的类别都是 read，因此计划轮次也能调用 `propose_plan`，执行轮次调用 `update_plan_step` 不必再审批。它们随轮次显隐：只有计划轮次把 `propose_plan` 交给模型；只有带着已批准计划的正常轮次才有 `update_plan_step`。
- `propose_plan` 成功后结束本轮。这是运行时的 `stopLoop`：工具结果先记下，循环再以 `completed` 结束，不发 `turn.aborted`。用户中止优先于这个结束。
- 用户的决定不走工具。主进程提供 `plan.approve`、`plan.replan`、`plan.abandon`。批准时可以改步骤标题，并写下 `plan.approved`（带批准时的计划）。没改过标题时，下一轮的用户消息用 Markdown 原文，否则按结构化字段重写。重新规划写下 `plan.rejected`（带说明）再以计划模式开一轮。放弃只写下不带说明的 `plan.rejected`。
- 最近一份状态为已批准的计划，会挂到之后的正常输入上，直到被新的已批准计划换掉。放弃或重新规划一份还没批准的计划，不会拿掉更早的已批准计划。

## 备选方案

- **把权限模式临时改成只读**：实现短，但会改掉用户的设置，也挡不住“始终允许”里已经写明的 allow 规则。强制拦截不会被这些规则覆盖。
- **让模型自己停下来**：计划提出后如果模型继续写文件，这一轮就不是只读的。`stopLoop` 在工具返回后结束循环。
- **升事件版本**：`content` 从字符串换成对象是不兼容的。这个事件从未落库，升版本会让所有旧会话的事件信封对不上，所以不升。

## 后果

- 系统提示词在计划轮次追加只读说明，在执行轮次追加已批准的步骤，并要求用 `update_plan_step` 报进度。
- 界面用计划卡片显示结构、进度和偏离说明。输入框用“计划”开关和 Shift+Tab 选择这一轮是不是计划模式。
- 工具的副作用（`plan.proposed`、`plan.step.updated`）由工具结果带出，运行引擎在 `tool.completed` 之后写入。工具自己不连接主进程。
